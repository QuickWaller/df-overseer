# doc-audit

Run after every deploy, and at least weekly regardless
(`docs/RUNBOOK-DEPLOY.md`'s standing cadence). You are checking whether what
this repo's docs SAY matches what the code, the registry/roster, and
`docs/STATE.md` (generated by `python scripts/drift_check.py --write-state`,
never hand-edited) actually show.

## Before anything else

1. Run `python scripts/drift_check.py --write-state` for a fresh
   `docs/STATE.md`. If it exits non-zero, that is real drift to report, not
   a reason to stop.
2. Read `docs/STATE.md`. It is generated, so trust its numbers over any
   hand-written figure anywhere else in the repo.
3. Read `CLAUDE.md`'s "Status" block at the top, `Working.md`'s "Current
   state" section, and `ROADMAP.md`'s `**Last reviewed:**` line.

## What to check

- **Per-role tool counts.** Any sentence of the shape "Role tool lists
  (...): **overseer N, architect N, ...**" (CLAUDE.md and Working.md both
  have one today) against `docs/STATE.md`'s own per-role counts. This is
  also covered mechanically by `tests/test_doc_facts.py` -- run it
  (`python -m pytest tests/test_doc_facts.py -v`) and treat a failure there
  as the same finding, not a separate one.
- **Service state claims.** "enabled"/"disabled", "active"/"inactive" for
  any named service, against `docs/STATE.md`'s Services section. Report
  the state; do not judge it (conductor.service disabled+inactive is a
  documented, deliberate state, not a bug to flag).
- **Deployed-commit / staleness claims.** Any doc that says a VM is "N
  commits behind," "up to date," or "redeployed," against
  `docs/STATE.md`'s "commits behind origin/main" column. A target with "(no
  stamp)" means `scripts/deploy.py` has never recorded a deploy there --
  say that plainly rather than guessing a commit.
- **Role/tool/file references that no longer exist.** Grep for a tool id,
  file path, or role name a doc mentions; confirm it still exists in
  `scripts/dfhack/TOOLS.yaml`, `agents/ROSTER.yaml`, or the filesystem.
- **README/runbook steps that contradict `infra/deploy-manifest.yaml`.** A
  runbook describing a deploy path the manifest no longer uses (or vice
  versa) is drift in one of the two; say which looks newer and why, don't
  silently pick one.
- **Dates and "as of" claims.** A sentence that says "as of <date>" is a
  frozen historical claim, not something to update to today's number --
  leave it alone. Only a sentence that reads as a CURRENT-state claim
  (no "as of", present tense, no date qualifier) is a candidate for "this
  is now stale."

## What to fix yourself, in one commit

Plain, mechanical factual drift only: a number that disagrees with
`docs/STATE.md`, a dead link, a file path that moved, a tool id that was
renamed. Use `docs/STATE.md`'s numbers directly; if a doc's own sentence
could instead POINT at `docs/STATE.md` rather than repeat a number by
hand, prefer rewriting it that way (fewer hand-written numbers to drift
next time), but don't restructure prose beyond what the fix needs.

Commit message should name what was fixed and cite the `docs/STATE.md`
generation it was checked against. No attribution lines.

## What NOT to touch

- `Working.md`, `decisions/DECISIONS.md`, `memory/*` -- these are the
  orchestrating session's own files (this repo's `handoffs/README`
  convention: concurrent streams writing one of these risks silent
  conflicts). Report what you found there; do not edit them.
- Anything that is a judgment call rather than a fact: whether a
  "proposed" design should now be called "done," whether a gap list
  item is still relevant, whether a ROADMAP bucket should move. List
  these for the orchestrator instead (see below).
- `CLAUDE.md` itself is borderline: its per-role tool-count sentence is a
  plain fact (fix it), but its narrative "Current state" prose is the
  orchestrating session's voice -- prefer flagging a narrative
  contradiction over rewriting someone else's sentence.

## Report back

1. What you fixed, in the commit (list the files and the specific
   corrections).
2. Judgment calls found but NOT made, one line each, addressed to the
   orchestrator: what looks stale, why you didn't just change it, and
   what deciding it would require (usually: asking the user, or checking
   live state this command doesn't have access to).
3. Anything `docs/STATE.md` itself could not answer (a target skipped for
   a missing env var, a check that degraded to "not verifiable") that
   blocked part of this audit.
