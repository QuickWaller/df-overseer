## Why

VM 106 went dark after architect run #3. It was reachable 23:17-23:35 UTC
2026-09-14, then no ping, no tcp/22, "QEMU guest agent is not running", CPU
near zero, no outbound traffic. A Proxmox API reset at 00:36 UTC 2026-09-15
booted for about a minute (CPU, disk and traffic rose), then went idle and
dark again. The user read the serial console: it reaches a login prompt, so
the kernel and getty are up and networking is what is gone.

Its PVE config looks normal (`net0` virtio on `vmbr0`, not link-down, static
`ipconfig0`, `agent: enabled=1`, `serial0` console). The live `home-lab`
session checked its records: no estate network change in that window, no
address collision in its IP registry, and no neighbouring VM touched since
2026-09-06. It has no console or host access either.

So the cause is almost certainly inside the guest, and it survives a reboot.
It came on at 23:35 **without** a reboot, after hours of working Docker runs.
Candidates worth checking, not conclusions: an unattended upgrade (netplan,
systemd-networkd, cloud-init, docker.io), a Docker network created during a
run whose subnet overlaps the LAN route, cloud-init re-running network config,
a full disk (a 4.58 GB image on a small root), or OOM.

**If we reinstall the same way without knowing the cause, it may go dark
again.** Hence the forensic step first.

## What to do

### 0. Record the starting config

Read VM 106's current config through the API and record VMID, name, memory,
cores, disk size, storage, `net0` model and bridge, `agent`, `serial0`, and
the fact of `ipconfig0` (the **fact** of a static address, never the value).
The rebuilt VM must match all of these.

### 1. Keep the old disk readable (best effort, timebox about 30 minutes)

Goal: a fresh VM 106 with the **old** root disk attached as a second disk,
read-only mounted, so the old journal can be read.

A route that should work, if the token has the rights:
1. stop 106;
2. full-clone template 102 to a temporary free VMID (check the PVE cluster
   and `../home-lab/inventory/hosts/*.yaml`, read-only, that it is unused).
   **Never start the temporary VM**; give it no cloud-init address;
3. detach 106's root disk (it becomes `unused0`, still kept);
4. reassign the temporary VM's disk to 106 as its root disk (PVE "move disk"
   with a target VMID), then attach the old disk as a second disk;
5. delete the empty temporary VM and confirm it is gone.

A cleaner route you find is fine. **If the token lacks a right, do not
widen its access or ask anyone else to.** Skip forensics, record which call
was refused and what it said, and take the plain route: destroy 106,
re-clone from 102 with the same VMID, name, memory and address, exactly as
`provision_vm.py` does.

### 2. Boot and verify reachability

SSH in, confirm ping, tcp/22 and the guest agent. **Note whether the fresh
guest agent is running**: if it is not, it probably never was, and "agent not
running" was never a symptom.

### 3. Diagnose from the old disk (if step 1 worked)

Mount the old disk read-only (`mount -o ro,noload` for ext4). Read with
`journalctl --directory=<mnt>/var/log/journal` and plain logs, focusing on
2026-09-14 23:15-23:45 UTC and the 2026-09-15 00:36-00:45 UTC boot.
Look at:
- `systemd-networkd`, netplan, NetworkManager;
- cloud-init (including `/var/log/cloud-init*.log`);
- dockerd and any `docker network` creation;
- apt and unattended-upgrades (`/var/log/apt/history.log`,
  `/var/log/unattended-upgrades/`);
- OOM, disk-full;
- `ip route` state if logged.

Also compare `<mnt>/etc/netplan/`, `<mnt>/etc/docker/daemon.json` and
`<mnt>/var/lib/docker/network/` against the fresh disk.

State a cause only if a log line shows it; otherwise list what was ruled
out and how. Quote the decisive lines (**mask any address, hostname or
subnet** before they reach your report or any file).

### 4. Reinstall openclaw, checking reachability after each step

Reinstall per the three openclaw handoffs:
- Docker from distro packages;
- the same image;
- `/opt/openclaw/` state and config, from the pinned config minus `_note`;
- the DeepSeek key by stdin, read with `grep -E '^KEY=' .env` and never the
  whole file.

**After every step, check the VM still answers on tcp/22 from the
workstation.** If a step kills it, stop there: that step is the cause, and it
is the most important finding of this stream.

**If step 3 found a cause, fix it before reinstalling.** Examples: pin
Docker's `default-address-pools` away from the LAN, or disable the offending
upgrade. Record the fix.

### 5. Soak

Reboot once, confirm it comes back, then confirm it is still reachable after
10 idle minutes. The original failure hit about a minute after boot.

### 6. Old disk

Once your report is written, **leave the old disk attached but unmounted**.
The orchestrator will ask the user before deleting it.
