# Stream: rebuild VM 106 (openclaw) in place, and find out why it went dark

**Written** 2026-09-15. **Status:** dispatched. **User go-ahead:** given
2026-09-15 ("im happy to destroy and rebuild", "can we work out what the

## Why

VM 106 went dark after architect run #3. It was reachable 23:17-23:35 UTC
2026-09-14, then no ping, no tcp/22, "QEMU guest agent is not running", CPU
near zero, no outbound traffic. A Proxmox API reset at 00:36 UTC 2026-09-15
booted for about a minute (CPU, disk and traffic rose), then went idle and
dark again. The user read the serial console: it reaches a login prompt, so
the kernel and getty are up and networking is what is gone.

Its PVE config looks normal (`net0` virtio on `vmbr0`, not link-down, static
`ipconfig0`, `agent: enabled=1`, `serial0` console). The live `home-lab`
session checked its records: no estate network change in that window, no
address collision in its IP registry, and no neighbouring VM touched since
2026-09-06. It has no console or host access either.

So the cause is almost certainly inside the guest, and it survives a reboot.
It came on at 23:35 **without** a reboot, after hours of working Docker runs.
Candidates worth checking, not conclusions: an unattended upgrade (netplan,
systemd-networkd, cloud-init, docker.io), a Docker network created during a
run whose subnet overlaps the LAN route, cloud-init re-running network config,
a full disk (a 4.58 GB image on a small root), or OOM.

**If we reinstall the same way without knowing the cause, it may go dark
again.** Hence the forensic step first.

## What to do

### 0. Record the starting config

Read VM 106's current config through the API and record VMID, name, memory,
cores, disk size, storage, `net0` model and bridge, `agent`, `serial0`, and
the fact of `ipconfig0` (the **fact** of a static address, never the value).
The rebuilt VM must match all of these.

### 1. Keep the old disk readable (best effort, timebox about 30 minutes)

Goal: a fresh VM 106 with the **old** root disk attached as a second disk,
read-only mounted, so the old journal can be read.

A route that should work, if the token has the rights:
1. stop 106;
2. full-clone template 102 to a temporary free VMID (check the PVE cluster
   and `../home-lab/inventory/hosts/*.yaml`, read-only, that it is unused).
   **Never start the temporary VM**; give it no cloud-init address;
3. detach 106's root disk (it becomes `unused0`, still kept);
4. reassign the temporary VM's disk to 106 as its root disk (PVE "move disk"
   with a target VMID), then attach the old disk as a second disk;
5. delete the empty temporary VM and confirm it is gone.

A cleaner route you find is fine. **If the token lacks a right, do not
widen its access or ask anyone else to.** Skip forensics, record which call
was refused and what it said, and take the plain route: destroy 106,
re-clone from 102 with the same VMID, name, memory and address, exactly as
`provision_vm.py` does.

### 2. Boot and verify reachability

SSH in, confirm ping, tcp/22 and the guest agent. **Note whether the fresh
guest agent is running**: if it is not, it probably never was, and "agent not
running" was never a symptom.

### 3. Diagnose from the old disk (if step 1 worked)

Mount the old disk read-only (`mount -o ro,noload` for ext4). Read with
`journalctl --directory=<mnt>/var/log/journal` and plain logs, focusing on
2026-09-14 23:15-23:45 UTC and the 2026-09-15 00:36-00:45 UTC boot.
Look at:
- `systemd-networkd`, netplan, NetworkManager;
- cloud-init (including `/var/log/cloud-init*.log`);
- dockerd and any `docker network` creation;
- apt and unattended-upgrades (`/var/log/apt/history.log`,
  `/var/log/unattended-upgrades/`);
- OOM, disk-full;
- `ip route` state if logged.

Also compare `<mnt>/etc/netplan/`, `<mnt>/etc/docker/daemon.json` and
`<mnt>/var/lib/docker/network/` against the fresh disk.

State a cause only if a log line shows it; otherwise list what was ruled
out and how. Quote the decisive lines (**mask any address, hostname or
subnet** before they reach your report or any file).

### 4. Reinstall openclaw, checking reachability after each step

Reinstall per the three openclaw handoffs:
- Docker from distro packages;
- the same image;
- `/opt/openclaw/` state and config, from the pinned config minus `_note`;
- the DeepSeek key by stdin, read with `grep -E '^KEY=' .env` and never the
  whole file.

**After every step, check the VM still answers on tcp/22 from the
workstation.** If a step kills it, stop there: that step is the cause, and it
is the most important finding of this stream.

**If step 3 found a cause, fix it before reinstalling.** Examples: pin
Docker's `default-address-pools` away from the LAN, or disable the offending
upgrade. Record the fix.

### 5. Soak

Reboot once, confirm it comes back, then confirm it is still reachable after
10 idle minutes. The original failure hit about a minute after boot.

### 6. Old disk

Once your report is written, **leave the old disk attached but unmounted**.
The orchestrator will ask the user before deleting it.

disk preserved and forensically read, openclaw reinstalled with a

**Forensics: the full best-effort route ran, no API call was refused.**
Sequence actually used (a refinement of the doc's suggested route, chosen
after finding no `OPTIONS`-based schema introspection is available on this
PVE version to pre-check the disk-unlink semantics): graceful ACPI shutdown
of 106, then a full clone of template 102 to temporary VMID 107 (confirmed
free both via `next_vmid()` and a read of `home-lab/inventory/hosts/SRV-01.yaml`,

survives in storage before ever running the same call against real data,
then detaching 106's real disk to `unused0` (confirmed non-destructive the
same way), then `move_disk` (VM 107 to VM 106, target `scsi0`), then
restoring `boot: order=scsi0` (this field came back empty after `move_disk`
and had to be set explicitly, worth remembering for next time), then
deleting the now-diskless VM 107 and confirming it gone (`next_vmid()` back

throughout (`svc-df-overseer-sandbox@pve`) had every right this required;
the only non-2xx responses seen were expected 403s probing VMID 107
*before* it existed (normal "not in our pool yet," not a rights gap) and
are not the kind of refusal the doc's fallback describes.

**A real incident, self-caused, found and fixed within this stream.**
Attaching the preserved old disk as a second SCSI device (`scsi1`,
hardware `ro=1`) *before* the fresh disk's very first boot caused the
guest's initramfs to select the **old** (hardware-read-only) disk as root
instead of the fresh one: both disks are full-clone lineage of the same
template and therefore share filesystem UUIDs and `/etc/machine-id`, and
udev's root-by-UUID resolution picked the wrong one when both were present
on the bus at boot time. Symptom was a ~20-minute non-boot indistinguishable
from the original incident from the outside (no SSH, ACPI reboot timed out
with "QEMU Guest Agent is not running ... VM quit/powerdown failed") until
`lsblk` inside the guest showed the smoking gun: root mounted on the 24G,
hardware-RO `sdb1` (the old, already-grown disk) while the fresh 25G `sda`
sat with its un-grown 2.5G template-original partition, untouched. Fixed by
force-stopping, detaching the old disk back to `unused0`, confirming a
clean single-disk boot (SSH up in 22s, `cloud-init status` reaching `done` in
under 90s), and only *then* hot-attaching the old disk to the
already-running guest (safe: an already-booted kernel doesn't re-evaluate
`root=` when a new block device appears). **Lesson for any future
forensic-disk-attach on a lineage-cloned VM: attach the second disk only
after the primary has completed its first boot, never before.**

**Cause of the original incident: not established from the guest's own
evidence, and this stream's own PVE task log resolves what looked like a
second, deeper mystery.** Read the old disk's `journalctl` across both
recorded boots:
- **Boot -1** (2026-09-12 06:22 UTC to 2026-09-15 00:35:01 UTC, the long
  run that went dark): normal SSH/`dockerd`/`containerd` activity matching
  the architect run through 23:34:11 UTC, then **only routine cron/sysstat
  entries** (23:35, 23:40, 23:45, 23:49 ...) with nothing abnormal at any
  point: no OOM, no disk-full, no docker-network error, no
  unattended-upgrade activity, no netplan/networkd error. The guest kept
  running internally (cron fired on schedule) well past the point external
  reachability was lost; this is not a crash or hang signature.
- **Boot 0** (2026-09-15 00:36:21 UTC to 01:31:45 UTC, after the
  Proxmox API reset mentioned in the brief): cloud-init finished cleanly in
  under 10 seconds with the **correct** static IP, mask, gateway and routes
  applied (an earlier grep-based pass of mine misread this as an empty
  route table; the unfiltered dump shows it was populated correctly, noted
  here so that false read doesn't propagate). Serial-console login
  attempts for user `df`/`root` are logged at 01:16:23 to 48 UTC,
  confirming the brief's "reaches a login prompt" observation and that the
  guest was genuinely healthy, not hung. **The boot ends in a complete,
  orderly ACPI poweroff**: `systemd-logind: Power key pressed short` /
  `Powering off` / a full, clean shutdown sequence through `Journal
  stopped`, all at 01:31:44 to 45 UTC. PVE's own task log (`/nodes/.../tasks`,
  read-only) resolves who sent that signal: a `qmshutdown` task,
  `svc-df-overseer-sandbox@pve`, 01:31:41 to 01:31:46, status OK. **This is
  this stream's own opening step** (the graceful shutdown issued
  before any of the disk work began), not a mystery second failure. So boot
  0's ending is fully explained and is this stream's own action, not new
  evidence about the original incident.
- **Ruled out, inside the guest, across both boots' complete text:** OOM,
  disk-full (old disk measured 30% used, 17G free, when mounted), a
  Docker-created network subnet colliding with the LAN route (no `docker
  network create`/bridge-driver error anywhere; the only docker0/veth
  activity matches short-lived `docker run --rm` containers with clean
  up/down transitions), an unattended-upgrade-triggered failure (the daily
  dpkg/apt units ran on their normal schedule with no errors; the only
  unattended-upgrades activity is its shutdown-hook service deactivating
  cleanly as part of *this stream's own* shutdown), and a cloud-init
  network misconfiguration on the post-reset boot (config was correct, per
  above).
- **Not established, and flagged honestly rather than forced:** why the
  guest was unreachable *from outside* (no ping, no tcp/22) for the final

  shutdown, when the guest's own OS and network configuration look entirely

  networking. That points at the host/vswitch/ARP layer, which is outside

## Orchestrator review, 2026-09-15

Spot-checked against the PVE API and a direct tcp/22 connect after the report
(addresses never printed): VM 106 running, name, memory, cores, `boot:
order=scsi0`, `agent`, `onboot` as reported, `scsi1` present with `ro=1`, no
`unused*` keys, tcp/22 open. Three corrections or additions:

1. **Not every disk flag matches.** The report says the rebuilt config matches
   the original "exactly except the disk's storage filename", and records the
   original root disk as `discard=on`, `ssd=1`. The live `scsi0` now reads
   only `...,size=25G`, with no `discard` or `ssd`. Low impact (thin-provision
   space reclaim and a guest hint), but it is a real difference, and one to
   set back.
2. **The rebuild does not show the cause was on the old disk.** The old guest
   was only ever *reset* while dark, never fully stopped and started. A PVE
   reset keeps the same QEMU process and its tap device on the bridge; a
   stop/start recreates both. This stream's shutdown, disk swap and fresh start
   changed the disk **and** the host-side network plumbing at once, so a
   stale tap/bridge/forwarding-table state is as consistent with the evidence
   as anything on the old disk. So is an address conflict from some other
   device that has since gone away. The guest's journal showing healthy
   networking with no outside reachability fits both. **Next time, the cheap
   discriminator is a full stop/start before any rebuild.**
3. "The final ~13 minutes of boot -1" does not match the timeline: external
   reachability was lost around 23:35 and boot -1 ended with the 00:36 reset,
   about an hour.

Also confirmed: the guest agent was never installed (so "agent not running"
was never a symptom), and the lineage-clone root-UUID collision is a genuine
new trap, now in `docs/TRAPS.md`.
