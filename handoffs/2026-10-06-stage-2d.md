`queue.close_legacy`, the conductor allowlist entries). Then ship `conductor/`

the whole directory is also safe; shipping `2547c52` alone is the minimum).
Operator commands, run on VM 106 in the conductor's checkout with its env file
(`--env-file` is optional when the service env is already exported):

    python -m conductor.cutover legacy --check    # changes nothing; lists every accepted ruling
    python -m conductor.cutover legacy --apply    # sets the cutover, closes each under the conductor's name

`--check` exits 0 clean, 1 on blockers, 2 on a failed call. `--apply` checks,
applies through `queue.cutover` (`set_cutover`, then `close_legacy` each, no
DFHack call), re-checks, and exits non-zero if anything is left; a crash is safe
to rerun. The same command with `rooms` is for 2b (it refuses until the legacy
cutover is set and rooms is frozen, and reminds the operator to flip `routed`).

Unexecuted wake, gated: `unexecuted_wake_ignore` is gone from `policy.yaml` and
`Policy`. The cycle keeps the store's own filtering (`queue.grade` already
excludes routed types, follow-ups and closed rulings, keyed on `proposal_id`),
suppresses the wake under an operator hold, and sends none until
`queue.cutover legacy` reports a cutover set (an unreadable read counts as not
set). So the order is safe either way: before `--apply` nothing wakes for the old
rulings, after it the list is only post-cutover work. Side effect to know: until
`--apply` has run, a genuinely new accepted-but-uncarried ruling also does not
wake the Overseer.

### The execute phase as built

`conductor/execute.py` (pure over a tool caller, state in `execute_state.json`
beside the cursors, wakes through `lane_state.json`), run by
`cycle._execute_phase` after the role loop. Order: read `queue.execution_state`;
resolve every Uncertain run (`queue.resolve_uncertain`, held with `hold` after
`uncertain_hold_after` unreadable results, proposer told); open projects and
apply follow-ups (a refused one is retried `refusal_limit` times); cleanup of
abandoned projects (`queue.cleanup_project`); reconcile issued steps
(`queue.observe`: `done` fires `step_done` once per step across both routes,
`stalled`, `blocked_material`, three `unknown` reads or a non-retryable failure
fire `step_attention` once per cause); idle projects (`project_idle` after
`idle_wake_ticks`, `queue.close` completed/idle after `idle_close_ticks` more);
then ready steps by urgency (`urgency_order`, as 2C delivers `preview.urgency`)
then age, at most `max_steps_per_cycle` (4), one `fort.quicksave` first. A
re-read happens after resolving or opening. A call that may have been sent
(`uncertain`) is never rerun in the same pass; it is resolved at the start of
the next. It never calls a clock tool, so it cannot resume the fort.

Gates (cycle): skipped for an escalation this cycle, or an operator hold without
`--allow-execution` (new `hold set --allow-execution`, `HoldState.allow_execution`,
literal true only, a corrupt file never allows it); a watchdog-owned pause and a
latched tripwire never reach it in the ordinary path. In `_tripwire_cycle` it runs
once, after the Overseer and before the verdict is acted on, with `latched=True`:
only open, apply, resolve and run, high urgency only (the server also enforces
this), never under an escalation or a plain hold. Stage T's sequence is untouched.

Wakes are lane data: `step_done`, `step_attention`, `project_idle` are
`wake_reasons` in `policy.yaml`, queued into `LaneState.pending` for the project's
proposer (the open project's `role`, remembered in state; else roles whose lane has
`execution: true`, the Architect). Policy block `execution:` holds every knob,
including `ore_hold_phase: '(_finish|_zone|_build)$'`.

Ore: a ready step whose `args.phase` matches `ore_hold_phase` is held, not run,
while this cycle's `blueprint.sites` read shows exposed ore or unclassified tiles
on `args.site` (`OreRead.unclassified` added), or the site or the whole read is
unreadable (held silently). It wakes the proposer once with `step_attention`
naming the materials and `construction.mine-vein-site`, and runs when the read
clears. The `step_attention` text says to file a follow-up or `queue.pass` to close.

Briefings: `queue.execution_state`'s optional `routing` block drives the Overseer's
ask (carry-out instruction names only unrouted types; routed ones are "run by the
conductor, rule only"), a per-proposal "Routed" line, an "ACCEPTED ROUTED WORK"
to-do line, and the Architect and Quartermaster `frozen` line ("skip this work",
the user's call). With no `routing` block everything is exactly as before.
