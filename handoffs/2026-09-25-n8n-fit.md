# Handoff: what could n8n add to df-overseer?

Date: 2026-09-25. **Researcher. Read-only. No VM, no fort, no deploy.**

## Why

The user uses n8n heavily in another project and likes it, and asks whether
it could be integrated into df-overseer nicely and what it would add. They
accept it would be a lot of work. This is exploratory: answer "what would it
add, and at what cost", not "build it".

## The questions

1. **What n8n is good at today**, from its current docs: triggers and
   schedules, webhooks, its AI agent and MCP nodes (both MCP client and MCP
   server trigger), human-in-the-loop and approval steps, error workflows,
   execution history, version control of workflows, self-hosting.
2. **Where df-overseer has a job n8n could do**, mapped to real components:
   the conductor's clock and wake loop, tripwires and notifications to the
   user, the proposal queue and rulings (a human approval step?), the wiki
   refresh timers (S8, not built), the series importer, reporting toward the
   public write-up, alerting when a guest goes dark, a user-facing dashboard
   or chat control. For each: what it would replace or add, and what we
   would lose.
3. **Where it must not go.** Test each candidate against the hard rules:
   the per-role allowlist is enforced server-side in `dfmcp` and is the real
   boundary (principle 8); one decider with advisors, no peer chat; no armok
   capabilities; never show a model a map; every call logged; the public
   repo holds no infra specifics. Would an n8n workflow calling the MCP
   server, or holding role tokens, widen access or bypass the audit trail?
4. **Reuse and operations.** The user weighs "what does a future project
   actually reuse" as a top-level criterion. Would n8n here share
   infrastructure or patterns with the user's other n8n use? Where would it
   run (name the VM role only; placing a guest is `home-lab`'s call, not
   this repo's), what it costs to operate, how workflows would be versioned
   in this public repo.
5. **A ranked shortlist**: the two or three integrations with the best value
   for the work, each with a rough size and the first small experiment that
   would test it, and an honest "not worth it" list.

## Result

Done, 2026-09-25. `research/2026-09-25-n8n-fit.md` answers all five questions.

**Bottom line: worth doing, narrowly.** n8n fits a small set of read-only
notification/ETL jobs this project has already named and deferred; it does
not fit anywhere near decision-making or write authority.

**Ranked shortlist:**
1. Escalation/tripwire → Telegram-style notification relay (S). Fills the
   named, explicit gap ("Telegram and the public feed later",
   `docs/AGENT-LOOP.md` §4). Pure read of `dfqueue`/Sentry status, no write
   capability.
2. Wiki mirror refresh timer, S8 (M). Not yet built; same job shape (fetch,
   diff, hold-back, store) the user's other project already runs weekly in
   production for a different source.
3. Read-only reporting digest toward the public write-up (S/M). Weakest of
   the three: assembles already-public material, and the register wants one
   curated voice, so this is a draft-assist at most, never auto-published.

**Hard-rule conflicts found:** none of the shortlist conflicts, provided n8n
only ever holds read-only role tokens issued the same way openclaw's are
(server-side `dfmcp` enforcement is unaffected by who calls it). The real
line is architectural, not technical: n8n must never hold a write-capable
role token or become a second locus of judgment (violates "one writer",
"one decider, no peer chat"), must never call DFHack directly (the RPC
socket's locality is why the MCP server stays on VM 103 at all), must reuse
`dfqueue.render.public_view()`'s allowlist and coordinate-scrubbing rather
than a raw snapshot if it ever renders anything, and must never become "the"
audit trail in place of `dfqueue`'s schema-validated, exportable one.

**Not worth it:** rebuilding the conductor's tick-aware clock/triage loop in
n8n; any n8n-orchestrated model call that can reach a write tool; n8n holding
any role token beyond read-only; a chat surface that can issue commands (as
opposed to read-only lookups, which openclaw's advisors already have);
treating n8n's execution history as an audit trail; a dark-guest alerting
workflow as a df-overseer-owned deliverable (plausibly `home-lab`'s).

**Reuse:** strong. The other project's git-sync tooling for n8n workflows
(stable per-workflow `id`s, strip-and-diff, re-arm-on-deploy) and its
MCP-server-as-read-only-reporting-surface pattern are both directly
transferable *approaches* (not copied code — the other repo is private and
nothing identifying was carried over). Credential handling
(env var working copy, canonical copy elsewhere, never in workflow JSON)
already matches this project's own `infra/local.*` convention.

**What could not be verified:** the "series importer" named in the brief
(found `series.*` read tools referenced in `dfmcp/README.md`, no standalone
importer component located); n8n's `Wait`/`Form` human-in-the-loop node
behavior (cited from the other project's house rule, not independently
re-verified against n8n's docs — both direct doc-page fetches attempted
404'd, recovered via search-engine summaries instead, a shallower form of
verification); whether n8n has a read-only SQL tool node suited to SQLite
(the other project's own example is Postgres-only); Telegram-node specifics;
exact operating cost in hours (evidenced qualitatively by three real bugs
the other project hit, not by a measured figure).

Full detail, evidence and citations: `research/2026-09-25-n8n-fit.md`.
