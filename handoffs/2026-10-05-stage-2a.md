Interpretations I am making where 6.1 is silent (all reported at the end):

1. **Ids.** A routed step id is `<project id>/s<N>`; its synthetic target is
   that same id (`targets: {set: [<step id>]}`). The step carries
   `proposal_id`. The project's proposer and declared `phases` are derived
   from `from_ruling -> proposal`, not copied onto the project record.
2. **Executor writes.** Roster `executor` (a top-level key) may write
   `project`, `executed`, `amend`, `close`; `observation` stays conductor.
   The sole writer still writes `ruling`, `escalation`, `abandon`. A
   sole-writer `project`/`executed`/`amend` whose ruling's proposal type is
   routed is refused in the store.
3. **Executor `executed`** keeps `ruling_id` (the project's root ruling, so
   the existing project lookup works) and gains optional `proposal_id` (the
   step's). An `executed` with `proposal_id` does not arm the prediction;
   `record_observation(done=True)` does, for the step's own proposal.
4. **Completion rule.** `executed` sets the synthetic target `issued` or
   `failed` (or `held`); `observation` with `done` flips it to `done`. The
   existing `step_prerequisites_satisfied` and `step_status` then agree.
5. **Cutovers** live in a `meta` table (`cutover:<group>`), raise-only.
   Rulings compare by queue order. Pending proposals are legacy when they
   are step-less and of the group's types (a pending proposal filed after
   the last ruling still counts, which a ruling-id bound could not do).
   Checking works with no cutover set (bound = highest ruling); applying is
   `set_cutover(highest)` then `close_legacy` per target, so a crash resumes.
6. **Filing rules in the store** for a proposal: a type in a routed group
   requires `step`; a frozen group refuses step-less with the freeze
   message; an unrouted group refuses `step`; `project_id`/`after_step` go
   together, name an open project the same role proposed, and a step of it.
7. **Atomicity.** `append` is split into a connection-level core so
   `apply_followup`, `open_project_from_ruling` and `close_legacy` read and
   write under one `BEGIN IMMEDIATE` (P2-L1). The amend base check (omit a
   previous step only if named in `drops`/`replaces`) applies to every amend.
8. Fix: `observation` validation used the original `steps` only, so an
   amend-added step could not be observed; it now uses the current version.

Open design gaps I expect to report: no source for a routed project's
`urgency` (kwarg, default normal); `public_title` is in the 2.1 example but
not in the 6.1 schema list (added as an optional proposal field); the
store cannot check the per-tool parts of "covered" or "each handle was
issued by this project" (carried arguments, handle argument names) because
those are `TOOLS.yaml` data, so 2C does them and the store checks the
structural parts.

**Store API as delivered (C calls only these).** `path` first, errors are
`store.QueueError`.

- `routing`: `group_of(type)`, `is_routed(type)`, `is_frozen(type)`,
  `coverage_on(type)`, `tools(group)`, `types(group)`, `group_of_tool(tool)`,
  `routed_groups()`, `routed_types()`, `routed_tools()`, `unrouted_types()`
  (what the ruling ask and the to-do line name), `retired()`. Data is
  `dfqueue/action_tools.yaml`; re-read when its content changes.
- `open_project_from_ruling(path, ruling_id, *, urgency=None, tick=None,
  snapshot="executor") -> project record`. One step `<project>/s1`, its own
  synthetic target, `proposal_id` set. Refuses non-accept, follow-up,
  unrouted, no step, ruling at or below the effective cutover, **no
  cutover set for the group** (unset means nothing opens), closed ruling,
  existing project.
- `apply_followup(path, proposal_id, *, tick=None, snapshot) -> amend record`.
  Under one lock; whole plan plus new step `<project>/s<N>` with
  `requires: [after_step]`, `proposal_id`, `adds`. Refuses unruled and
  uncovered, rejected, closed or abandoned project, already applied, bad
  `after_step`. The store's amend base check backs it.
- `check_step_runnable(path, project_id, step_id, *, latched) -> list[str]`
  (`[]` runnable): project open, ruling accepted, step in the current
  plan, **step has a `proposal_id` and its tool and args equal that
  proposal's step**, proposal is the project's own or an accepted/covered
  follow-up of it, prerequisites done, not issued/done/failed, no `issuing`
  or `held` run, tripwire not latched unless the project's `urgency` is
  `high`.
- `begin_step_run(path, project_id, step_id, *, tick, baseline) -> run_id`
  (re-checks runnability, tripwire excepted; `step_id` may be
  `cleanup:<handle>`, unchecked against the plan);
  `finish_step_run(path, run_id, executed: dict, *, handle=None) ->
  {"run", "executed"}`: `executed` is `{actions, notes?, cycle?, snapshot?}`;
  the store fills role, `ruling_id` (the project's root ruling),
  `step_id`, `proposal_id`. To move the target add `targets: [<step id>]`
  and `target_state` in `issued|held|failed` to an action; **omit both on a
  first failure so the step stays retryable**. `done` is refused here.
  `handle` defaults to the first string in `game_refs`.
  `unresolved_step_runs(path)` lists `issuing` runs;
  `resolve_step_run(path, run_id, outcome, handle=None, *, tick, notes)`
  with outcome `success` (handle required, appends the `executed`, run
  `resolved`), `transient` (run `void`, step retryable) or `held` (run
  `held`, step blocked); `get_step_run`, `step_runs(path, project_id,
  step_id=None)` (history, for retry counts), `issued_handles(path,
  project_id)`.
- `record_observation(path, project_id, step_id, *, tick, done, detail,
  snapshot) -> observation`. `done=True` is the only way to `done` and arms
  the step's proposal prediction at `tick + check_after_ticks`; the step
  must be `issued`. `detail` may carry `status`, `reason`, `hold_code`; the
  rest is stored bounded and coordinate-scanned.
- `close(path, *, target_id, outcome, reason, cleanup=None, tick=None,
  snapshot)` (prefix of the id picks project, proposal or ruling);
  `close_legacy(path, target_id, *, reason, tick=None)`; `legacy_targets(path,
  group="legacy")` (entries `{kind, id, group, ruling_id, proposal_id,
  executed, summary}`; legacy: every accepted ruling up to the cutover or,
  before one is set, the highest ruling; a routing group: its accepted
  rulings, open Overseer-written projects, pending step-less proposals);
  `set_cutover(path, group, ruling_id)` (raise-only, `"legacy"` is a group),
  `cutover(path, group)`, `highest_ruling(path)`.
- `open_projects(path) -> list[dict]` (the one WIP definition; entries
  `{project_id, from_ruling, group, role, urgency, summary, status,
  steps_open, phases_remaining}`), `unexecuted_accepted_proposals(path)`
  (unrouted, no follow-ups, no closed rulings, covered by `proposal_id` or
  ruling id), `projects_awaiting_cleanup(path) -> [{project_id, handles}]`
  (abandoned routed projects not yet closed, for 4.4).
- `pending_proposals` now excludes covered and closed proposals;
  `project_status` is unchanged in shape.

### Design problems and calls to confirm

1. **No source for a routed project's `urgency`.** `check_step_runnable`
   lets `high` run under a latched tripwire and the cap lets `high` exceed
   it, but neither a proposal nor a ruling carries urgency (6.1 has no
   field). I added a keyword to `open_project_from_ruling`; 2C/2D must
   decide where it comes from (a proposal field, or the ruling).
2. **`public_title`** is in the 2.1 example but not in 6.1's schema list;
   added as an optional proposal field, copied to the project.
3. **`close` outcome for a project:** 6.1 says `completed` if an `executed`
   record exists. For a legacy project that would label a half-run project
   completed on the public Board, so `close_legacy` uses `completed` only
   when `project_status` reads `done`. A ruling uses the `executed` rule as
   written.
4. **Per-tool filing checks are 2C's:** the store checks structure only.
   Whether `after_step` is the step that applied the previous declared
   phase, "each handle was issued by this project" (use `issued_handles`),
   carried arguments for coverage, the template phase list and the
   meta-overlap refusal need `TOOLS.yaml` data. `covered_by` is set by the
   server at filing and must name a step of the project.
5. **Rollback hazard:** an executor may write only for a routed type, so
   flipping a group back to `routed: false` strands its live executor
   projects (their steps cannot be recorded). Flip `frozen`, not `routed`,
   to pause; or relax this check if a rollback path is wanted.
6. **`pending_brief` must switch to `open_projects`** (it counts
   `project_status == active`, which the design says disagrees with the
   cap, P3-M3); that is in `dfmcp/queue_tools.py`, a 2C file.
7. **2b `--check` lists less than the design implies:** deploy 2a closes
   every accepted ruling, so by 2b "accepted room rulings without
   `executed`" are already closed and `legacy_targets("rooms")` lists
   only what 2a did not close: open legacy projects (their rulings stay
   closed, the projects do not) and pending step-less proposals, plus any
   ruling made since 2a.
8. **A cutover must be set for a group before anything opens**
   (`open_project_from_ruling` refuses an unset cutover, including after a
   flip of `routed: true`): safe. `close_legacy` of a pending proposal also
   needs its group's cutover, so the 2b `--apply` order is `set_cutover`
   (at the highest ruling), `close_legacy` each, then flip `routed`.
9. **Existing bug fixed in passing:** `observation` validation used the
   original `steps`, so an amend-added step could not be observed.
