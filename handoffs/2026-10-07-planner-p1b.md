### Simpler-reading choices

1. `PlanPolicy.enabled` is a second switch beside the roster flag, so a deploy of the roster
   alone wakes nothing; the enable commit flips both.
2. A rejection is inferred (a serving proposal id vanished and the position fell), because
   `plan.status` does not report rulings. An abandoned proposal also reads as one.
3. A reload resets the season cursor and owed review; a backoff set further in the future
   than its cap re-arms.
4. `plan_watch.json` is saved by the cycle (not in dry runs); a corrupt file wakes nobody
   and is never silently reset.
5. The Planner's pinned openclaw config is not in the repo (pinned configs live only on the
   agents VM), so there is nothing to commit for it; see the live steps.
