# How stairs work in DF 53.16 / DFHack 53.16-r1.1, and the right way to connect z168 to z167

Read-only research. Primary sources: this workstation's installed DFHack
53.16-r1.1 (`C:\Program Files (x86)\Steam\steamapps\common\DFHack\hack\scripts\internal\quickfort\dig.lua`
and `build.lua`, opened in full), this repo's own `df-overseer-diggable.lua`
and the two 2026-09-17 handoffs that built and live-tested `find-stair`/
`dig-stair`, the decision register, and two DF wiki pages (fetched, current
v53.16 revision per the page's own header). VM 103 was not touched; the
local Windows install runs the same DFHack version DFHack itself reports
(`memory/dfhack-environment.md`), so a source read here is treated as
describing VM 103's code too, though the live *behavior* already observed on
VM 103 (the farm/stair live test) is the higher-confidence source wherever
the two overlap.

## Summary

Digging is the right primitive to reach z167 stone from z168, exactly as
this project's `dig-stair` already does: a down stair designated on the
already-open z168 floor tile plus a matching up stair on the hidden z167
wall tile directly beneath it, both in one call, because DF will not create
a job for either half alone (the 2026-09-10 boundary-connectivity trap,
confirmed again by source today). Constructing a stair is not a better
primitive here and should not replace digging: constructions need already-
open space, and virgin stone at z167 is a solid wall, so nothing can be
*constructed* there until something is dug first. The live test's real
failure was not a design problem with "both halves in one call", it was
that `dig-stair`'s candidate ranking never checks for a building sitting on
the upper tile, and quickfort's dig mode silently no-ops a dig designation
under a building while still reporting success. That is a fixable gap in
`ranked_stair_candidates`/`dig_stair_down`, not a reason to change the
primitive.

## Mechanics, with confidence per claim

### 1. Dig designations for stairs

Source: `dig.lua`, opened directly, this install, 53.16-r1.1. **High
confidence, primary source, this exact version.**

Three designation values exist (`df.tile_dig_designation`): `UpStair`,
`DownStair`, `UpDownStair`. Three quickfort `#dig` symbols map onto them:

| symbol | designation | admits (tile revealed) | admits (tile hidden) |
|---|---|---|---|
| `u` | UpStair | WALL or FORTIFICATION only | any tile, unconditionally |
| `j` | DownStair | WALL, FORTIFICATION, a diggable floor (FLOOR/BOULDER/PEBBLES), a removable shape (ramp/up-stair/down-stair), a shrub, or a sapling, anything but a tree or a construction | any tile, unconditionally |
| `i` | UpStair→UpDownStair, or a plain diggable floor→DownStair only | WALL, FORTIFICATION, a diggable floor, or an existing up-stair | any tile, unconditionally |

For a **hidden** tile every one of these designates unconditionally, no
shape or material read at all, quickfort's own header comment states this
directly ("if the tile is hidden, we designate blindly to avoid
spoilers"). This is exactly what `df-overseer-diggable.lua`'s ACT/SENSE fix
already relies on (2026-09-16), now confirmed again by reading the same
function `i`/`u`/`j` all funnel into.

`i` (up/down stair) is **not** simply "always both directions." Reading
`do_up_down_stair` precisely: on a solid WALL/FORTIFICATION tile, or on a
tile that is already an up-stair, it designates `UpDownStair` (both
directions through one tile). On a tile that is **already an open floor**
(already dug, no stair present), it designates `DownStair` only, because
the tile is already passable from above, so there is nothing to dig
"upward" through. This matters for this project: at z168, the upper
candidate tile is already an open, walkable farm-room floor, so `i` there
would behave exactly like `j` (down-stair only), not like a true
up-down-stair. `j` is the correct, simpler symbol for that tile, which is
what `starter-entrance-1x1.csv` already uses.

**Pairing and order:** DF creates a real dig job only once both halves of a
connected stair pair exist as matching stair designations on adjacent
z-levels at the same x,y, the exact 2026-09-10 register trap ("a plain
floor dig beneath a completed stair never becomes a job unless the
connecting tile is itself a matching stair type"). Nothing in `dig.lua`
requires a particular *order* between the two designation calls: each is an
independent write to `flags.dig` on its own tile, and the engine's own job
creation (triggered by `dfhack.job.checkDesignationsNow()`, called once at
the end of `do_run`) evaluates the map fresh, not incrementally per call.
So designating the upper down-stair, then the lower up-stair (or the
reverse) is equally valid, and either can be designated while the other
level is still fully hidden, nothing in `do_down_stair`/`do_up_stair`
reads the other z-level's state at all. `dig-stair`'s existing "both in one
call" design is correct on this point already: order doesn't matter, only
that both end up designated.

**Digging a down stair into a floor** (soil/grass, as at z168): confirmed
directly from `is_diggable_floor` (`FLOOR`/`BOULDER`/`PEBBLES` shapes,
material not checked), a grass floor's shape is `FLOOR` the same as any
other dug floor, so `do_down_stair` admits it. **This confirms
`df-overseer-diggable.lua`'s own header conclusion** ("this repo's source
reading did not find the mechanism the recorded trap describes") **a
second time, independently, today.** The `docs/TRAPS.md` "downstair can't
be designated on grass" line still has no confirming mechanism anywhere in
`dig.lua`. Cost: digging into an already-open floor for a down-stair, or
into a hidden or wall tile for either symbol, has no material cost at
design time, DFHack's dig designation itself never touches inventory; the
cost is only the dwarf-labor to actually carve it (mining skill/time), not
consumed materials, confirmed by `dig_tile`'s action functions, which only
write designation flags.

### 2. "Half" vs "full"

Not a term the wiki or DFHack source uses verbatim (checked both:
`Stairs` wiki page, fetched, makes no mention of "half"/"full" stairs).
**Moderate confidence, inferred from the enum, not a cited term:** the
three designation values map cleanly onto the user's framing, `UpStair`
or `DownStair` alone is a "half" stair (passable in one vertical direction
only), and `UpDownStair` is a "full" stair (passable in both directions
through the same tile, no separate stair needed on the tile directly above
or below it to keep going). The standard way down through virgin rock is
exactly what this fort's original entrance/connector pair already does and
what `dig-stair` reuses: a down stair (half) on the upper level plus an up
stair (half) on the lower level, together forming one full connection
across the z-boundary, this is the vanilla-UI-standard pattern, not a
project invention. **Yes, you can dig just the down stair and have miners
(or a later tool call) dig the next level from it once it's carved**, but
only in the sense that the *carved* up-stair tile becomes walkable and
extends the network; the *designation* half needs its lower-level partner
designated too, or no job is ever created for either half (2026-09-10
trap). "Dig the down stair, then dig from there" is exactly how a fresh
box-scan `find`/`dig` call would proceed once the up-stair is actually
carved and walkable, that's `dig-stair`'s own stated design (chaining
into the existing box-scan primitive rather than digging the room in the
same call).

### 3. Constructed stairs

Source: `build.lua`, opened directly, this install. **High confidence for
the mechanics; moderate confidence for material rules**, which live in
engine C++ code, not in any Lua quickfort validates against, quickfort's
own `is_valid_tile_construction` checks placement only, never material.

Symbols `Cu`/`Cd`/`Cx` (`build.lua` lines 948–956) build
`df.construction_type.UpStair`/`DownStair`/`UpDownStair` as a real
building (`building_type.Construction`), not a dig designation. Placement
(`is_valid_tile_construction`, defaulting to it for every `Construction`
type at line 1086–1087) requires `is_valid_tile_has_space_or_is_ramp`:
`EMPTY`, `FLOOR`, `BOULDER`, `PEBBLES`, `RAMP_TOP`, `BROOK_TOP`, `TWIG`,
`SAPLING`, `SHRUB`, or `RAMP` shape, **open or already-clear space, never
a solid WALL**. This is the load-bearing fact for this project: **a
constructed stair cannot be placed into virgin, undug stone.** You dig
into rock; you construct into open air or an already-clear floor. That
makes construction irrelevant for reaching z167 stone from z168 today , 
z167 is entirely hidden, solid wall.

Materials (wiki, `Construction` page, fetched, states "v53.16"; **not
independently confirmed against this install's own filter code**, grepped
`building.lua`/`build.lua` for an explicit material/job_item filter tied to
`Construction` types and found none, meaning the actual item-acceptance
rule is enforced by the game engine itself, not by any Lua this project can
read): boulders, logs, blocks, or bars of any solid material are all valid
directly, raw logs **can** be used without turning them into blocks
first, contrary to the general assumption that only blocks work. Glass is
the one exception (block form only). This is a live correction worth
recording for Uniboslan specifically: the fort's 3 owned logs *could*
construct a stair, if construction were the right primitive here, it
isn't, for the reason above, but it would matter the day this fort wants a
stair in open space above ground with no rock to dig.

A player would build rather than dig when there is no rock to dig, an
above-ground tower, a bridge approach, anywhere the stair needs to exist in
open air. Not this project's current situation.

### 4. Alternatives: channels and ramps

Source: `dig.lua`, opened. **High confidence.**

`h` (channel, `do_channel`) admits WALL/FORTIFICATION/a diggable
floor/an existing down-stair/a removable shape/gatherable/sapling (same
admit-list shape as down-stair, minus up-stair) on a revealed tile, or
unconditionally on a hidden one. It removes the tile's floor entirely
(a real, permanent hole one tile can't easily undo), and the standard DF
side effect, not itself scripted in this Lua, it's engine behavior, is
that material falls to the level below and typically leaves a ramp there.
Channeling is the tool for an open shaft (light, drop point, moving
liquid or units down fast) or for making the tile below become a ramp
automatically; it is a worse choice than a stair pair for a *walkway* dwarves
should use constantly, since a hole isn't itself walkable, only the ramp
that forms below it is, and channeling consumes the original floor
permanently rather than leaving both levels intact and connected.

`r` (ramp, `do_ramp`) uses the same admit rule as plain mining (WALL or
FORTIFICATION only on a revealed tile) and designates `dig_ramp`. A ramp
lets units walk between z-levels without a matching stair on the far
side, provided the tile above the ramp's top is open (`RAMP_TOP`/`EMPTY`).
Ramps are the natural choice for vehicle-width or wide gradual
transitions (e.g. a wagon route) and are what channeling produces as a
side effect; they are not the normal choice for a narrow single-tile
fortress stairwell, which is what this project needs at z168/z167.

**Recommendation for this project: stairs remain the right choice**,
matching the existing `dig-stair` design and the fort's own already-working
entrance/connector precedent. Channel/ramp are alternatives worth knowing
about, not a reason to change course here.

### 5. Blockers

Source: `dig.lua` `do_run_impl` (lines ~838–855), opened, this install.
**High confidence, and this closes an open question from the live test.**

For every dig-mode action *except* smooth/engrave/track (which tolerate
`Passable`/`Dynamic` occupancy) and traffic-designation actions (which
skip the occupancy check entirely): **`if digctx.occupancy.building ~= 0
then goto inner_continue end`**, any building at all on the tile, not
just an obstacle-flagged one, silently skips that tile's whole action.
Critically, this `goto` happens *before* either of the two stat counters
(`dig_designated` or `dig_invalid_tiles`) increments, so a skipped tile
shows up in **neither** stat, the only way to detect it from `quickfort`'s
own output is that `dig_designated`/`"Tiles designated for digging"` is
lower than the number of tiles the caller expected, or by reading the real
designation flags back. `quickfort run` still returns `CR_OK` regardless
,  exactly what the farm-stair live test found happening to the z168
Stockpile tile (`downstair_ok:true`, `downstair_stats:
{"Tiles designated for digging": 0}`, and a direct read-back confirmed
`dig_designation=0`, nothing designated).

**Correction to the live test's own report:** its Findings section
attributes this to "the same `check_tiles_and_extents` occupied-tile skip"
used for `#zone`/`#place`. Reading the actual source shows this is not
literally the same function. `check_tiles_and_extents` (`building.lua`
line 517, called from `build.lua`/`place.lua`/`zone.lua` for buildings,
placements and zones) is a *different*, building/zone-specific
validity pass. `#dig` mode never calls it at all, the occupancy check
that blocked the stockpile tile is `dig.lua`'s own separate, simpler
inline `occupancy.building ~= 0` test inside `do_run_impl`. Both produce
the same *symptom* (an occupied tile is silently skipped, `CR_OK`
regardless), which is presumably why the executor's report described them
as "the same", but they are two independently-maintained code paths that
happen to agree on this behavior, not one shared function. Worth a
`docs/TRAPS.md` correction if anyone revisits that entry, since a future
reader might go looking for `check_tiles_and_extents` inside `dig.lua` and
not find it.

Hidden tiles: never blocked, designated blindly (section 1). Aquifers and
liquid: not checked anywhere in `dig.lua` at all, a `flow_size`/liquid
check exists in `build.lua`'s `is_valid_tile_base` (used for buildings/
zones), not in the dig path, which is exactly why this project's own
`dig-stair` handoff added a separate, manual aquifer/liquid check
(`water_table`, `flow_size`) as an *operator*-side safety gate before
calling `dig-stair` for real, rather than relying on quickfort to refuse
anything. That operator-side gate is still necessary; nothing in `dig.lua`
provides it. Grass and soil: not blockers (section 1). Map edge: `if
digctx.on_map_edge then return nil end` on every dig action except
chop/track/toggle-marker/remove-construction/item flags, a genuine but
irrelevant blocker for Uniboslan's interior farm room.

### 6. quickfort blueprint symbols, and one blueprint covering both levels

Confirmed directly: `d`=mine, `h`=channel, `u`=up stair, `j`=down stair,
`i`=up/down stair, `r`=ramp, `z`=remove ramps, plus the smoothing/track/
item-flag/traffic symbols (`dig.lua` `dig_db` table). Construction stairs
use `Cu`/`Cd`/`Cx` under `#build` mode (`build.lua`), a completely separate
blueprint mode from `#dig`.

**One CSV blueprint is always exactly one z-level** (confirmed:
`quickfort list`'s own doc line, "Blueprints are .csv files or *sheets*
within .xlsx files", a `.csv` blueprint is one sheet, one z). A single
`.xlsx` workbook *can* hold one sheet per z-level and quickfort's
`--repeat up/down,N` flag exists specifically to reapply a (possibly
multi-sheet) blueprint at successive z offsets, per the doc's own pump-
stack example ("each repetition... is 2 z-levels"). There is also a
`#meta` blueprint mode (`meta.lua`, opened) that can chain named
sub-blueprints, including ones at different z-offsets, in one `quickfort
run` call. **None of this changes the recommendation for this project**:
`dig-stair`'s two-CSV, two-call design (`starter-entrance-1x1.csv` at
`upper_z`, `starter-connector-1x1.csv` at `lower_z`) is the standard,
already-working shape for a CSV-based stair connector, and is functionally
identical to what a `#meta` blueprint would do under the hood. A `#meta`
blueprint could collapse it to one `quickfort run` invocation instead of
two, which is a real but low-priority simplification, not a correctness
fix, see Recommendation 4 below.

### 7. DFHack helpers

**`dig-now`** (`hack/docs/docs/tools/dig-now.txt`, present, **not** tagged
`unavailable`) instantly completes real, non-marker dig designations , 
"as if a miner were doing the mining," including turning a `DownStair`/
`UpStair` designation into the real carved tile, without needing a dwarf
to path there or take the job. This exists on the local Windows install;
**not independently confirmed live on VM 103** (same DFHack version, so
presumptively present, but not checked against the actual VM 103 binary
this session, flagged as unverified, matching this project's own "check
the local install before assuming API surface exists" rule). It is tagged
`armok` (an out-of-character, magic-tier tool), so using it during normal
unattended play would be a different kind of cheat than the knowledge-scope
violations this project already guards against, appropriate for a fast,
deterministic *test* of "does this designation actually produce a walkable
tile" (bypassing miner pathing and wait time entirely) but not something
to wire into the agents' normal play loop. No DFHack `dig-now`-style
capability is currently used anywhere in this repo's tools.

`quickfort` itself (`run`/`list`/`orders` etc.) is the only other relevant
helper, already the one this project's tools use throughout.

## Recommendation: fixing `dig-stair`

The design, both halves in one call, no `KIND`/room argument, dig rather
than construct, is right and should not change. Four concrete fixes,
smallest first:

1. **Don't trust `*_ok`. Report and check the real tile count.**
   `dig_stair_down` already gets `quickfort_stats` back from each call
   (`parse_quickfort_stats`); it just never looks at it. Add a check:
   `downstair_designated = (downstair_stats["Tiles designated for
   digging"] or 0) >= 1`, same for `upstair`, and surface both booleans
   in the return value distinctly from `*_ok`. This alone would have
   caught the live test's failure without any raw designation read-back
  , the stats line already said `0` for the skipped tile.

2. **Read the designation back for real proof, not just the stat.** The
   stat count is quickfort's own self-report; a direct
   `dfhack.maps.getTileFlags(pos).dig` (or the block-level equivalent)
   read after both calls is the only thing that can't be fooled by a
   quickfort-side accounting bug. Cheap to add (two reads, no mutation),
   and matches this project's own "verify the verification" rule.
   Suggest adding it inside `dig_stair_down` itself (not leaving it to
   every caller to reimplement, which is what this stream's own live
   test had to do by hand with a throwaway script).

3. **Skip occupied candidates in `ranked_stair_candidates`, don't just
   report the failure after the fact.** Add a building-occupancy check at
   the *upper* candidate tile (`dfhack.maps.getTileFlags(x,y,upper_z)`'s
   `occupancy.building`, or `dfhack.buildings.findAtTile`) alongside the
   existing `walkable_group`/`is_diggable` checks, the same shape as
   `is_diggable`'s existing pattern. This is strictly better than
   catching it after a real designation call: a caller doing a dry run
   today gets a candidate that looks fine and then silently fails for
   real, exactly what happened live. The lower tile doesn't need this
   check, a building cannot sit on undug rock, so it's structurally
   impossible there; skip it there for the same reason `is_diggable` never
   checks it now, not by oversight.

4. **Optional, low priority: collapse two `quickfort run` calls into
   one.** A `#meta` blueprint referencing both `starter-entrance-1x1.csv`
   and `starter-connector-1x1.csv` at their respective z-offsets could
   replace the two separate `dfhack.run_command_silent` calls with one.
   This changes nothing about correctness (both already happen inside one
   `dig_stair_down` invocation with no live-fort mutation in between) , 
   only worth doing if the two-call shape ever becomes an actual
   maintenance or atomicity problem, which it hasn't yet.

None of this argues for a single down-stair alone as "the better
primitive", that is precisely the shape the 2026-09-10 trap already
rejected, confirmed again by reading `dig.lua` today: a lone half never
becomes a job. Nor does it argue for constructing rather than digging , 
z167 is solid, hidden rock, and constructions cannot be placed there at
all until something has already been dug.
