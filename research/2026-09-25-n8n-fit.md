# n8n fit for df-overseer

Date: 2026-09-25. Researcher, read-only. Answers
`handoffs/2026-09-25-n8n-fit.md`.

## Bottom line

**Worth doing, narrowly.** n8n is a good fit for a small number of read-only,
notification-and-ingestion jobs this project has already named and deferred
("Telegram and the public feed later", the wiki refresh timer, S8). It is a
bad fit for anything touching decision-making, write authority, or the fort
itself — those are exactly the places `docs/AGENT-ARCHITECTURE.md` spent the
most design effort locking down (one writer, one decider, server-side
allowlists, a typed audit trail), and n8n does not do any of that job better
than what is already built. The honest framing: **n8n is a notifier and an
ETL tool for this project, not a second brain and not a second writer.**
Treat every candidate below as "does this only read, and does it only notify
or ingest" — the moment a candidate would let n8n decide something or hold a
write-capable credential, it drops to the "not worth it" list regardless of
how well n8n could technically do it.

The user's other project (a separate private work repo, described here only
in pattern form, never by name or identifier) has already done the hard part
of answering "is n8n worth the operational cost at all" — real production
use, real bugs found and fixed, a real git-versioning scheme for workflows.
That derisks the "should we invest in n8n as infrastructure" question
generally; what's answered here is the narrower "which pieces of df-overseer
specifically" question.

## 1. What n8n is good at today

Marked by source: **[n8n docs]** for n8n's own documentation (fetched or
searched live, 2026-09-25), **[this repo]** for df-overseer's own source and
docs, **[other project, pattern]** for the user's other n8n use, described
generically.

- **Triggers and schedules.** A Schedule Trigger node (cron-like) and a
  Webhook Trigger are core, well-documented primitives. **[other project,
  pattern]** runs several weekly schedule-triggered pulls from a billing API
  into Postgres today, in production, on a self-hosted instance.
- **AI agent and MCP nodes, both directions.** n8n ships both an **MCP
  Server Trigger** node (n8n acts as an MCP server, exposing attached tool
  nodes to an external MCP client) and an **MCP Client Tool** node (an n8n
  AI Agent calls an external MCP server as a tool) **[n8n docs,
  docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger]**.
  The MCP Server Trigger defaults to **no authentication** and needs Bearer
  or header auth explicitly turned on **[n8n docs, same page]** — a real gap
  to check before ever exposing one, not a solved default.
- **Human-in-the-loop / approval steps.** A `Wait`/`Form` node pattern for a
  human approval gate is a named, supported shape **[other project,
  pattern's own house rule: "its `Wait`/`Form` over a hand-rolled approval
  step"]**, not independently re-verified against n8n's docs by this pass,
  but the other project's own binding rule cites it as real and in active
  use for an accounting-approval design.
- **Error workflows and retry.** Every workflow can name a fallback **Error
  workflow** in its settings, which runs when the workflow errors **[n8n
  docs, via search: docs.n8n.io/flow-logic/error-handling and
  docs.n8n.io/build/flow-logic/handle-errors-gracefully]**. Per-node
  **Retry On Fail** (max 5 tries, max 5000ms between) is separate and
  interacts with the node's own `On Error` setting: setting `On Error` to a
  "Continue" mode makes the retry setting a no-op — the node continues on
  first failure rather than retrying **[n8n docs, same search]**. **[other
  project, pattern]** independently arrived at the same "branch don't throw"
  discipline by hand: explicit `Switch`-on-status-code branches rather than
  relying on the generic error path, because a generic error path buries the
  status code inside a string.
- **Execution history.** Every run is logged by the engine itself, inspectable
  per node, per item. **[other project, pattern]** found this genuinely
  useful for debugging a live production pull, but also found it is **not**
  the same thing as a durable, exportable, schema-validated audit record —
  see §3.
- **Version control of workflows.** n8n has **no first-class git integration**
  for community/self-hosted workflow JSON as of this check. **[other
  project, pattern]** built its own bidirectional-aware, one-directional
  (git → n8n only) sync tooling from scratch: stable per-workflow `id`s
  (n8n's importer matches by `id`, not name — a workflow file with no `id`
  imports as a brand-new duplicate every single deploy, found the hard way,
  six duplicate copies), a field-stripping diff (`versionId`, `createdAt`,
  `active`, `pinData`, and others are instance-local and must be stripped
  before comparing, but a node's own internal `id` must survive stripping or
  the file corrupts), and a "deploy re-arms what was already armed" fix
  after discovering n8n's importer **silently deactivates every workflow it
  imports**, schedules included, with nothing in the CLI output that says
  so. None of this is n8n behavior described in its docs; all of it was
  found by testing the real installed version and reading its source
  (`dist/commands/execute.js`, `tag.repository.js`). **This is the single
  most load-bearing finding for df-overseer's own decision**: n8n's
  "workflow as source of truth" story is not something you get for free by
  reading the docs, and a public repo that adopted n8n would need to build
  or reuse this same tooling, not just add workflow JSON files.
- **Self-hosting.** **[other project, pattern]** runs it self-hosted, two
  Docker containers (n8n + its own Postgres), on a VM on a private network.
  df-overseer already has a directly analogous deployment (`dfmcp-server`
  on VM 103, LAN-bound, bearer tokens the only guard, Tailscale deferred),
  so the operational shape is not new to this project even though the tool
  would be.

## 3. Where it must not go

Tested against the hard rules named in the brief, each against real source
in `docs/AGENT-ARCHITECTURE.md`.

- **The per-role allowlist is enforced server-side in `dfmcp`, and stays the
  real boundary regardless of what calls it.** `dfmcp/roles.py`'s
  `Roster.check` runs on every `tools/call`, keyed off a bearer token
  resolved server-side (`dfmcp/auth.py`), never off anything the caller
  claims — this is explicitly designed to hold even when the caller is a
  different trust level (`docs/AGENT-ARCHITECTURE.md` §13: "client-side
  enforcement is not enforcement"). An n8n workflow calling the MCP server
  is just another client at that boundary, structurally identical to
  openclaw. **It does not widen access or bypass the audit trail by
  existing** — but only if it is issued its own role token like any other
  caller, never the Overseer's, and never a shared/blanket credential. This
  is the same discipline the other project's own `.env`/credential-registry
  split already practices for a different reason (rotation, not roles), so
  the pattern is not new to the user.
- **One decider with advisors, no peer chat.** This is the rule most at risk.
  n8n's own AI Agent node, or any n8n workflow that calls a model and then
  acts on the answer, is structurally a second decision path if it can reach
  any write tool. §7's "single writer" argument is not about tidiness — DF
  has no transaction boundary, and a second writer (even a rarely-used one)
  reopens exactly the corruption risk this design spent real effort closing.
  **Verdict: n8n may read, notify, and ingest. It may not hold a
  write-capable role token, and it may not be the thing that decides whether
  a proposal is accepted.** A workflow that turned an `escalation` record
  into "ask a model whether to resume" and then called `clock.resume` would
  violate this even though every individual step looks harmless in
  isolation — the violation is architectural (a second locus of judgment),
  not a bug in any one node.
- **No armok capabilities.** n8n adds no new capability to the game; the
  boundary is still exactly `dfmcp`'s tool registry, unchanged by who calls
  it. Not a real risk here as long as the previous point holds — a
  read-only role token cannot reach an armok-tagged tool because the roster
  never grants one, not because n8n is well-behaved.
- **Never show a model a map.** Not directly implicated by anything on the
  shortlist (all read-only text/counts), but worth stating as a standing
  constraint on any future n8n dashboard: `dfqueue/render.py`'s
  `public_view()` is already a field **allowlist**, not a redaction, proven
  by a test that a new field never leaks by default
  (`dfqueue/tests/test_render.py`). Any n8n-built dashboard must read
  through that same allowlist (or an equivalent one), never a raw snapshot,
  and must never render a coordinate — `dfqueue/schema.py` already scans
  every free-text field for raw-coordinate patterns and refuses them at
  write time, which is the discipline a dashboard would need to inherit,
  not reinvent.
- **Every call logged.** `dfmcp/server.py` logs one JSON line per
  `tools/call` to `dfmcp.calls` regardless of caller, so n8n's calls are
  covered by the same mechanism openclaw's are — this holds automatically,
  not because n8n does anything extra. What does **not** come for free:
  n8n's own execution history is a second, differently-shaped log (per-run,
  per-node, not append-only-audit-record-shaped). **This must never become
  "the" audit trail for anything that matters** — `dfqueue`'s schema-
  validated, coordinate-scrubbed, exportable design is a real, considered
  piece of infrastructure (§10's four record types, "the failure mode is
  letting doctrine be written directly from an agent's self-assessment");
  n8n's execution log is operational debugging output, not a replacement.
- **Public repo, no infra specifics.** Directly solved, not just avoidable:
  the other project's `docs/n8n-sync.md` pattern (git owns workflow JSON
  with a stable chosen `id`; credentials live in n8n's own encrypted store,
  referenced by name, never by value, in the committed file; a `.env`
  working copy with a canonical copy elsewhere) is exactly
  df-overseer's own existing `infra/local.*` / gitignored-`.env` shape,
  independently arrived at. Reusing it costs nothing new in discipline.

## 4. Reuse and operations

- **Shares infrastructure/patterns with the user's other n8n use: yes, and
  substantially.** The git-sync tooling (stable ids, strip-and-diff,
  re-arm-on-deploy, one-file-at-a-time import to dodge the tag-collision
  bug) is real, tested, production-proven tooling built to solve a problem
  df-overseer would hit on day one if it adopted n8n and workflow JSON in
  git. It cannot be imported directly (the other repo is private and this
  session was told not to copy anything identifying), but the **approach**
  is exactly the kind of "what does a future project actually reuse"
  candidate the user's own standing criterion asks for — this is a case
  for building a small shared `n8n-sync` tool (or documenting the pattern in
  this repo) rather than rediscovering the same six-duplicate-workflow and
  silent-deactivation bugs here.
- **The MCP-server-as-read-only-reporting-surface pattern is the strongest
  single transferable idea found.** The other project runs a live workflow
  (described here only by shape, not name) that uses an MCP Server Trigger
  node plus a set of parameterized, read-only query tools against its own
  database, plus a small feedback-loop table so an external caller can leave
  structured feedback on an answer. That is functionally identical to what
  df-overseer would want for "let the user ask the fort's history a
  question without a new role or a new write path" — except df-overseer
  already has this, structurally, via the Consultant's and any advisor's
  existing read-only MCP tool grants. **The honest finding: n8n does not add
  a capability here that dfmcp doesn't already have** — it would only add a
  second interface (chat-shaped, outside openclaw) onto data dfmcp already
  exposes. Worth doing only if the user specifically wants a chat surface
  independent of openclaw; not worth doing to gain read access that already
  exists.
- **Where it would run.** Per `docs/AGENT-ARCHITECTURE.md` §13, the split is
  about trust boundaries: DFHack + the MCP server stay on VM 103 because
  DFHack's own RPC socket is local and unauthenticated, and nothing here
  changes that calculus for n8n specifically — n8n would talk to the
  *already-authenticated* MCP HTTP endpoint, the same way openclaw does, not
  the raw DFHack socket. So n8n does not need to be on VM 103, and probably
  should not be — same class of reasoning that put openclaw on its own VM
  (holds credentials, restarts a lot during iteration, blast-radius
  separation from the public relay). **Naming a VM role only, not an
  identity**: n8n's natural role is "another MCP-calling client that holds
  read-only role tokens," the same shape as openclaw, so it belongs wherever
  that class of component belongs — plausibly alongside openclaw if the
  user is fine with one more service sharing that host's blast radius, or on
  its own guest if not. **Actually placing a guest is `home-lab`'s call, per
  this repo's own upstream-obligations rule, not decided here.**
- **What it costs to operate.** Not zero, and the other project's own
  experience is the evidence: a self-hosted n8n instance is another Docker
  stack, another version to track (found real behavior differences tied to
  the specific installed version, 2.40.5, not documented upstream), and at
  least three real footguns already hit in production there (undeclared
  `id` causing duplicate imports, silent deactivate-on-import, one-file-at-
  a-time import to dodge a tag-uniqueness crash). Budget for "n8n has its
  own maintenance surface," not "n8n is free because it's just config."
- **How workflows would be versioned in this public repo.** Same answer as
  the other project's, and it is a genuine constraint worth stating plainly:
  **hand-authoring n8n workflow JSON is unpleasant**; the honest workflow is
  build-in-the-UI, capture, read the diff, commit, then treat the UI as
  read-only. That UI step happens against a running n8n instance holding
  real (if read-only) credentials — meaning some of this project's iteration
  would happen against a live service, not purely in the repo, which is a
  different rhythm than this project's Lua/Python-and-tests workflow.

## 5. Ranked shortlist

**1. Escalation and tripwire notification relay (Telegram or similar).**
Size: **S**. This is the best value-for-work candidate because it fills a
gap this project has already named and explicitly deferred rather than
speculatively invented one — `docs/AGENT-LOOP.md` §4 item literally says
"Alerts: a status JSON and journald lines. Telegram and the public feed
later." It is pure read-and-notify: n8n would poll (or be pushed, if a
webhook is added later) the `escalation`/pause state already written to
`dfqueue` and the Sentry's status JSON, and turn it into a message. No new
role token capability beyond read access, no new decision path, no map, no
infra specifics (the bot token is exactly the kind of secret the existing
gitignored-`.env` / credential-registry pattern already handles). **First
experiment**: a single n8n workflow, Schedule Trigger (e.g. every 60s) →
read `dfqueue`'s exported `records.jsonl` (or a small new read-only
`queue.overview`-shaped MCP call once n8n has a role token) → filter for a
new `escalation` record or a `pause`-state Sentry status since last run →
Telegram message. Success criterion: a real tripwire firing on the live fort
produces a Telegram message within the polling interval, with no fort write
involved anywhere in the chain.

**2. Wiki mirror refresh timer (S8).** Size: **M**. Explicitly not built yet
("the first real pull needs the user's go-ahead and a contact string" per
this repo's own status banner), and the job shape (periodic HTTP fetch,
diff against the last snapshot, hold new content back for a week, tag
provenance, store) is close to exactly what the other project already runs
weekly in production for a different data source. Read-only against the
public internet, never touches the fort, fits the Consultant's existing
"untrusted data, never instructions, at most a prior" framing without
needing to change it. **First experiment**: wrap the existing
`wikimirror/` Python refresh logic behind an n8n Schedule Trigger using an
Execute Command node (lowest-risk first cut — reuses the already-built and
presumably-tested Python rather than reimplementing wiki-diffing logic
natively in n8n nodes), gated the same way the user's other schedules are
(disarmed until a deliberate go-ahead). Success criterion: one real
unattended weekly run that produces the same output the manual run would
have, with the hold-back and provenance tagging intact.

**3. Read-only reporting digest toward the public write-up.** Size: **S/M**.
Weakest of the three, ranked third on purpose: it assembles already-public
material (`evals/live/*/README.md`, `dfqueue`'s JSONL export) rather than
filling a named gap, and the project's own register explicitly wants one
curated voice, which an auto-digest can assist but not replace. **First
experiment**: a manually-triggered (not scheduled) n8n workflow that reads
the past week's `evals/live/` entries and `dfqueue` export and produces a
draft summary as a file or a draft message — never auto-published, always a
draft a human reads before it becomes register prose, respecting this
project's existing "publishing is outward-facing, gate it each time" rule.
Success criterion: the draft is genuinely useful as a starting point for
the next `Working.md`/register update, judged by whether a human keeps more
than half of it.

## What's not worth it, and why

- **Rebuilding or replacing the conductor's cycle/triage/clock logic in
  n8n.** It is built, deployed, and its whole point is being tick-aware in a
  way n8n's wall-clock scheduler is not. This would be a rebuild of working,
  carefully-reasoned code (the `f·T + k` ticks-per-cycle arithmetic,
  §6) for a tool that does not natively model the thing being optimized.
- **An n8n AI Agent (or any n8n-orchestrated model call) that can reach a
  write tool.** Structurally a second decider even if it is rarely used or
  "just for edge cases." §7's single-writer argument is about DF's lack of a
  transaction boundary, not about tidiness, and it does not weaken because
  the second writer is n8n instead of a second agent role.
- **n8n calling DFHack directly, or holding any role token beyond
  read-only.** No candidate on the shortlist needs this, and adding it
  would be adding a new trust-boundary crossing purely to make a future
  candidate easier, which is backwards — the boundary should stay minimal
  until a specific write-capable use case is actually decided, not
  provisioned speculatively.
- **A chat interface that can issue commands to the fort**, as opposed to
  read-only queries. Same objection as the AI Agent point above, phrased for
  the "user-facing chat control" item the brief asked about directly: fine
  as a read-only lookup surface (arguably redundant with what already
  exists via openclaw's own MCP access, per §4), not fine as a control
  surface.
- **Treating n8n's execution history as an audit trail.** It is real and
  useful for debugging n8n itself, but it is not schema-validated,
  coordinate-scrubbed, or built for public export the way `dfqueue` is.
  Nothing here should ever be the only record of a decision.
- **Alerting on a dark guest, as a df-overseer-owned workflow.** The
  detection and runbook already exist and are estate infra; per this
  project's own memory ("home-lab owns infra fixes"), even the notification
  half plausibly belongs to `home-lab`, not here — flagged as a case where
  the honest answer is "someone should build this, possibly in n8n, but
  probably not as a df-overseer deliverable."

## What could not be verified

- **The "series importer" named in the brief.** This pass found `series.*`
  history-read MCP tools referenced in `dfmcp/README.md`'s tool table but no
  standalone importer component in the parts of the tree read for this
  brief. Not chased further given the read list the brief specified;
  flagged rather than guessed at.
- **n8n's `Wait`/`Form` human-in-the-loop node behavior**, cited above from
  the other project's own house rule rather than independently re-verified
  against n8n's docs in this pass (the two direct doc fetches attempted for
  this research both 404'd on the exact URLs tried; the error-handling and
  MCP findings above were recovered via search-engine summaries of n8n's
  docs pages instead, which is a shallower form of verification than a
  direct source read and is flagged as such).
- **Whether n8n's MCP Server Trigger, in the specific installed version the
  other project runs, actually supports a read-only-safe deployment against
  a database as narrow as `dfqueue`'s SQLite** — the other project's own
  example uses `postgresTool` nodes against Postgres; `dfqueue` is SQLite,
  and whether n8n has an equivalent read-only SQL tool node, or whether this
  would need a thin wrapper, was not checked against the installed n8n
  version.
- **Telegram (or any specific notification backend) integration specifics**
  — not checked against n8n's docs at all in this pass; assumed available
  based on general knowledge that it is a common, well-supported n8n node,
  not independently confirmed here.
- **Exact cost/maintenance burden in wall-clock hours** — the "not zero"
  claim in §4 is evidenced by three real bugs the other project hit, not by
  a measured hours figure, because no such figure exists to cite.
