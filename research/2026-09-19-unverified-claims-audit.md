# Audit: claims presented as measured that are not

Date: 2026-09-19. Offline, read-only stream. No VM, no SSH, no fort, no file
changes except this document. Produced for
`handoffs/2026-09-19-unverified-claims-audit.md`; read that file, `CLAUDE.md`
and `docs/PURPOSE.md` first for the four known instances this sweep was
dispatched to find more of.

## Method, stated plainly

Read in full: `CLAUDE.md`, `docs/PURPOSE.md`, `docs/PRODUCTION-MODEL.md`,
`docs/TRAPS.md`, `Working.md`, `ROADMAP.md` (top status block and changelog),
`doctrine/seed.yaml` (all 784 lines), `doctrine/validate.py`,
`handoffs/2026-09-19-water-doctrine-correction.md`,
`handoffs/2026-09-17-water-source-zone-test.md`, and
`scripts/dfhack/df-overseer-{labor,well,stocks,zone,trees}.lua` in full.
Grepped every file under `scripts/dfhack/*.lua` for lookup-then-default
patterns (`df.X[NAME]` used as a key, `pcall` failures falling through to a
bare `return 0`) and read every hit in context. Spot-checked
`production/{blocker,cover,snapshot}.py`. Read targeted windows of
`decisions/DECISIONS.md` (recent entries, and the entries a grep for
"verified working" and similar phrases pointed at).

**Not fully read, grep-scanned only for the lookup/default pattern above:**
`df-overseer-{chokepoints,connectivity,diff,diggable,openarea,orders,
overview,stuckjobs,threat,ui,breach,landmarks}.lua`. A full read of those
twelve files (about 4,500 lines) did not fit this pass; the pattern search
covers the specific highest-value failure mode the handoff named, not every
possible issue in those files. Also not read: most of `research/*.md` (69
files) beyond the ones the findings below needed; `handoffs/*.md` beyond the
ones cited; `memory/*.md`. Everything reported below is from a file I
actually opened, cited by path and line.

## What I checked and found genuinely solid (for calibration, not padding)

- `scripts/dfhack/df-overseer-labor.lua`'s `set_labor`/`autolabor_enabled` (lines 262-336): refuses outright on an unresolvable labour name or an indeterminate autolabor state, rather than guessing. This is the fix that followed the `FEED_WATER_WOUNDED` incident, and it holds up on a direct read.
- `scripts/dfhack/df-overseer-stocks.lua`: extensive, dated, self-critical header documenting three successive miscounts of the same fort's food in one day, each correction dated and reasoned through (`flags.foreign` vs `flags.trader`, item-count vs stack-unit count). The current code matches the header's claims on a line-by-line read.
- `production/blocker.py:228-246` (`_available`): explicitly distinguishes "no stock entry at all" (returns the graph node's own status, e.g. `UNAVAILABLE`) from "entry present, zero available" — the same distinction whose absence caused the `FEED_WATER_WOUNDED` bug. Read as correctly implemented.
- `production/snapshot.py:1-60`: unusually explicit about its own gap (which of the four deduction flags shipped tools actually read today: only `trader`, none of `in_job`/`owned`/`forbid`), citing exact line numbers in three other files for each claim. Spot-checked two of the three citations (`df-overseer-stocks.lua:190-194`, `df-overseer-well.lua:200-204`) and both match.
- `decisions/DECISIONS.md`'s 2026-09-12 "Threat detector LIVE-VERIFIED" row: concrete counter-evidence given (a fox and weasel admitted by reachability alone with no danger flag; two real demons correctly excluded, cross-checked by direct query). This is a different tool from the `unit-status hostile` filter `docs/TRAPS.md:105-108` separately (and correctly) warns is untrustworthy — the two claims are about different code and do not contradict each other, despite reading similarly at a glance.
- `docs/PRODUCTION-MODEL.md:234-240` ("One unresolved inconsistency, do not paper over it") and `doctrine/seed.yaml`'s `cover-target-not-yet-settable` entry (lines 732-784): both are model examples of the standard this audit is checking for — an open question stated as open, with the number that would settle it named but not invented.

## Cheap to settle

Ordered by how little it costs to close:

1. **Findings #1 and #2 (PRODUCTION-MODEL.md §12 and the doctrine entry).** Both are already fully scoped by `handoffs/2026-09-19-water-doctrine-correction.md`, which was written for exactly this purpose. The single action is running that stream to completion (or checking whether it is already running and just hasn't landed yet) — no new investigation needed, the finding and the fix are the same document.
2. **Finding #6 (broken citation).** One command: `ls research/2026-09-17-water-source-zone-test.md` (fails) vs `ls handoffs/2026-09-17-water-source-zone-test.md` (succeeds). Fix is a one-line path correction in `Working.md:254` once someone is editing that file for another reason.
3. **Finding #4 (Working.md stale HANDOVER section).** No investigation needed, purely an edit: either move the `HANDOVER 2026-09-17` section's drinking claims below the correction with a forward pointer, or add one sentence at the top of that section noting it is superseded by the section above.
4. **Finding #3 (the four count-or-zero functions).** Cheap to *harden*, not cheap to *prove currently wrong or right* without a live DFHack connection. The observation that would settle "is this producing a wrong number right now": run each of `df-overseer-trees.lua`'s, `df-overseer-workshop.lua`'s two, and `df-overseer-well.lua`'s lookup against the live install once (`dfhack-run lua "print(df.unit_labor.CUTWOOD)"` and equivalents for `BREWER`/`COOK`/`MASON`/`MECHANIC`/`CARPENTER`/`BOULDER`/`WOOD`/`BLOCKS`/`BARREL`) and confirm none returns `nil`. That is a single read-only command per name, no mutation, already the kind of check this project runs routinely. The *fix* (make each function return an explicit error/null instead of 0 on an unresolved name, matching `set_labor`'s pattern) is a small, mechanical, low-risk change once someone is authorised to touch those files.
5. **Finding #5 (the self-serve-drinking contradiction).** Not cheap. Settling which observation was right needs either a fresh live read of the same three founders' thirst/position history, or an honest note added to both documents stating the conflict is unresolved. The second is cheap; the first needs the fort.

## Note on scope discipline

I found fewer new instances than the four already on record might suggest are out there. The repository's own recent habit — dated corrections left in place rather than silently edited away, explicit "not verified" and "unresolved" notes, a doctrine format whose header states its own rules — is working in most of the places I checked. The dangerous residue is concentrated in exactly two places: a design document and a doctrine entry that a dispatched correction stream has not yet reached, and a class of lookup-then-default code that was fixed in one file after the incident but not propagated to its three siblings.
