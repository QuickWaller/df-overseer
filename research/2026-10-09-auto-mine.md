# Auto-mine dig mode: semantics, Lua flag, safety, tool changes (2026-10-09)

Tags: **[V]** verified against a primary source (installed build, live struct read, pinned upstream
source, wiki mirror text). **[I]** inferred. **[U]** could not be checked.
Everything here was read-only: live struct introspection and file reads on the fort VM, the offline
wiki mirror (SQLite opened read-only), and upstream DFHack source fetched to a scratch dir.
Build checked: DFHack 53.16-r1.1 (`dfhack.getDFHackVersion()` live), wiki mirror pages tagged 53.16.

## Answer in brief

1. **Modes.** The game's own enum, read live, is `df.mine_mode_type = {NONE=-1, ALL=0,
   AUTOMINE_NON_LAYER_MATERIAL=1, MARK_ECONOMIC_ONLY=2, MARK_GEMS_ONLY=3}` **[V]**, held in
   `game.main_interface.designation.mine_mode` **[V]**. UI keys: `m; n` opens advanced options, then
   `v` all, `V` automine, `o` ores+gems only, `g` gems only (wiki "Designations menu" r316036)
   **[V as wiki text]**. "Auto" follows **non-layer material** (veins and clusters of any
   inclusion stone), which is wider than the wiki's "ore/gems" wording **[I from the enum name;
   DFHack's own emulation keys on `veinMaterialAt != -1`, same notion]**. It does not follow plain
   layer rock. This enum-versus-wiki wording difference is a finding in itself.
2. **Lua flag.** `tile_occupancy.dig_auto` (a bit next to `dig_marked`), present and readable live
   **[V]**. Set it on the same tile as `designation.dig = Default`. The only block flag involved is
   `block.flags.designated = true`, which quickfort already sets **[V]** and a direct-write path
   must set too. **Quickfort has no auto marker** (markers are `mb`, `mw`, `md` only) and its source
   never touches `dig_auto` **[V]**. So auto needs a small post-pass after `quickfort run`.
3. **Safety.** Auto-follow designations are ordinary dig designations, so the game's damp/warm
   cancellation applies to them like any other **[I, strongly supported]**; the DFHack warm/damp-dig
   tag exists precisely to let an autodig vein pass through light aquifer, and we do not use it
   **[V]**. **Nothing in the game protects against breaching a cavern or open space**: there is no
   pre-dig cancel, only a post-hoc announcement (`FEATURE_DISCOVERY`, "You have discovered an
   expansive cavern deep underground") **[V]**. Hidden water or magma not adjacent to a dug tile
   gives no warning **[V as wiki text]**.
4. **Our tools.** One `dig_mode` argument (data on the template, plus a flag on direct digs), one new
   leaf module that writes `dig_auto` after designation, and a small poller that diffs designated
   tiles against what we intended and checks the new ones with the existing reservation and hazard
   modules plus a new open-space check. Section 4.

**Biggest caution for the plan:** following starts only when a dug auto tile is itself vein material.
Straight hallways through plain rock follow nothing, and hallways that pass beside a vein without
cutting into it follow nothing. In the game UI, automine mode cannot even designate plain rock.

## 1. Modes and semantics

- Live: iterating `df.mine_mode_type` printed the four values above; `mine_mode` is 0 (ALL) on the
  paused fort **[V]**.
- Wiki mirror, page "Designations menu" r316036, chunk "Designations modification": `m;V;1`
  "Automining Ore/Gems - Once this tile has been processed, all neighboring tiles will be marked for
  mining, if they contain the same ore or gems. Can only be designated on revealed ores/gems. Will
  appear green." `m;o;1` ores/gems, `m;g;1` gems only, "Only works on revealed tiles." The Mining
  page says switching to automining lets you "quickly assign mining tasks to entire veins". Vein and
  cluster automining arrived in 0.40.20 (version-history chunk) **[V as wiki text]**.
- DFHack `dig` docs in the install (`docs/tools/dig.txt`, `digtype`): applies automatic mining
  "(designates uncovered neighbouring tiles of the same type to be dug)" **[V]**.
- DFHack source (upstream `plugins/dig.cpp`, develop branch fetched today; not diffed against the
  exact 53.16 tag **[U]**): `do_autodig` starts from the dug tile's `veinMaterialAt(pos)`, returns if
  it is `-1` (plain rock), then visits the **eight same-z neighbours** and matches only tiles of the
  **same vein material**. This is DFHack's re-implementation for the warm/damp case, not vanilla's
  code, but it mirrors vanilla's rule **[I]**.

Consequences:

- **What it follows:** the same vein or cluster material as the tile just dug, not "any ore"; a vein
  of non-economic inclusion stone counts, since the enum says non-layer, not economic **[I]**.
- **Across z-levels:** DFHack's emulation propagates same-z only. Vanilla cross-z behaviour is
  **[U]**; plan on no cross-level following, so a vein is followed level by level only where our digs
  expose it on each level **[I]**.
- **Indefinitely:** each newly dug auto tile re-propagates to its own revealed same-material
  neighbours, so a vein is followed until exhausted or a cancel or obstruction stops it **[I from the
  wiki's "all neighboring tiles will be marked"]**. Nothing found limits distance. Veins can run into
  cavern walls (wiki "Cavern": breaching "a variety of ores and gems lining its walls will be
  revealed") **[V as wiki text]**.
- **Starting condition:** see the caution above **[I]**; the UI-only restriction is **[V as wiki
  text]**. Via Lua we can set the bit on plain Default-dig tiles; whether the game ignores or
  mishandles the bit on a plain tile is **[U]**.
- **Priority of followed tiles:** **[U]** (probably the default).
- **Trap, DFHack source comment:** "Auto dig only works on default dig designation. Setting dig_auto
  for any other designation prevents dwarves from digging that tile at all." So only ever set the bit
  where `dig == Default` (never channel, stair or ramp) **[V as source comment]**.

## 2. Setting it from DFHack Lua

```lua
local blk = dfhack.maps.getTileBlock(x, y, z)
if blk.designation[x % 16][y % 16].dig == df.tile_dig_designation.Default then
  blk.occupancy[x % 16][y % 16].dig_auto = true
  blk.flags.designated = true
end
```

- `dig_auto` and `dig_marked` both exist on `df.tile_occupancy` in the installed build **[V]** (live
  `printall` of a block's occupancy bits).
- Quickfort's installed `internal/quickfort/dig.lua` writes only `occupancy.dig_marked` (marker mode,
  lines ~345 and ~675-682) and sets `block.flags.designated = true` (~672) **[V]**. The quickfort
  guide's dig markers are blueprint (`mb`), warm (`mw`), damp (`md`) **[V]**. A blueprint cannot
  express auto.
- DFHack's own `digtype` writes `dig = Default` plus `occupancy.dig_auto`, and clears `dig_auto` for
  any non-Default dig **[V as source]**.
- No automine-specific block flag exists in `block.flags` (`designated`, `update_temperature`,
  `update_liquid`, ..., `has_aquifer`, `check_aquifer`, ...) **[V]**.

## 3. Safety

- **Damp/warm cancels.** The game's `DIG_CANCEL_DAMP` (52) and `DIG_CANCEL_WARM` (51) fire when a
  miner is about to dig beside aquifer or magma stone **[V]** (`df-overseer-digcancel.lua`,
  `research/data/2026-09-23-announcement-types.tsv`). Evidence that auto-follow tiles are not
  exempt: DFHack's `dig` docs say the warm/damp marker "is propagated along with the autodig
  designation ... easily autodig a mineral vein that goes through a light aquifer", and its NEWS
  carries "don't leave phantom dig designations behind when autodigging warm/damp designated tiles"
  **[V as docs and changelog]**. Without the tag they cancel like any dig **[I]**. Our scripts never
  set the warm/damp tag (grep of `scripts/dfhack`) **[V]**, so the protection holds, with caveats:
  - Since 53.12, two **standing orders** ("Mining cancelled near new damp stone", "... warm stone")
    turn the cancel off (wiki "Standing orders", "Digging designation canceled") **[V as wiki
    text]**. The fort's current setting was **not read [U]**. The user's "no watcher for damp/warm"
    call assumes both are on, which is the default. Worth one read before relying on it.
  - The cancel fires per newly revealed damp tile, so a followed vein through a light aquifer stops
    at the first damp tile (the safe outcome) and leaves a cancelled tile our `digcancel` module
    already reports with its position **[V]**.
- **Water or magma with no damp/warm sign.** Per the wiki, a tile is damp/warm only if fluid is
  beside, above or below, and "most of the time, you don't know which"; digging upward stairs gives
  no warning **[V as wiki text]**. Auto-follow uses plain dig only, so the upward-stair gap does not
  apply **[I]**.
- **Caverns and open space.** No game cancel exists (wiki "Cavern" treats opening one as a risk to
  manage, with no warning feature). The only announcement is `FEATURE_DISCOVERY` (id 2 in our tsv;
  text confirmed on the wiki "Announcements.txt" page), which fires after the breach **[V]**. Whether
  it carries a usable `rep.pos` is **[U]**. `STRUCK_MINERAL` (4) and `STRUCK_ECONOMIC_MINERAL` (5)
  exist and are a cheap "auto is following something" signal; their `pos` is also **[U]**.
- **Other follow-on effects, no protection:** auto tiles can run into reserved footprints, cut walls
  we want intact, and open our planned chokepoints. The user accepts veins crossing reserved space
  and miners pulled onto ore (decision 2026-10-09).

## 4. Minimal tool changes

Where designation happens today: `df-overseer-blueprint.lua` `apply_phase` (quickfort `run`, around
line 1234), `df-overseer-diggable.lua` dig and stair paths (`quickfort run`),
`df-overseer-construction.lua` `mine-vein`.

1. **Mode argument.** Per the generalisability rule, put it in data: an optional `dig_mode`
   (`standard` default, `auto`) in the template metadata (`blueprints/templates/<id>-v<n>.yaml`) and
   as one optional trailing arg on `blueprint apply` and `diggable dig`. Not in the CSV, since
   quickfort cannot express it.
2. **One new leaf module** (e.g. `df-overseer-automine.lua`): `mark(tiles)` sets `occupancy.dig_auto`
   for each tile whose `designation.dig == Default`, skips every other dig kind (the trap above),
   sets `block.flags.designated`, and returns counts (`marked`, `skipped_non_default`). Call it right
   after `quickfort run` returns OK, over the tile list the apply already computed for its
   reservation check. Dependency-free like `df-overseer-hazard.lua`.
3. **Watcher (light).** A per-cycle poll over blocks with `flags.designated`, against a ledger of
   designations we issued (`df-overseer-ledger.lua` is the natural home). Any dig designation or
   `dig_auto` bit not in the ledger is "auto-followed". For each new tile:
   - `reservations.check_tiles(tiles)` (existing; with no `res_id`, any tile inside a reservation is
     refused/returned) **[V as read]**. Outcome: report, do not cancel (the user accepts veins in
     reserved space), and let the Manager decide.
   - `hazard.check_tile(x, y, z)` (existing) flags a tile that is, or touches, a revealed aquifer or
     magma tile, a pre-warning before the game's own cancel; its band rule covers hidden neighbours.
   - **New open-space check** for cavern or void: a neighbour that is revealed, non-wall and not in
     our own dug-tile ledger. A hidden cavern cannot be read without breaking the no-armok rule, so
     prevention is impossible for an unseen cavern. The reaction path is `FEATURE_DISCOVERY` (and any
     revealed open neighbour) triggering containment: clear `dig_auto` and the dig designation on
     auto-added tiles within a radius (a player eraser power, not armok), then notify. Which tile
     fields mark "cavern" (`designation.feature_local`, `feature_global`, `subterranean` exist) is
     **[U]** until read on a real cavern.
   - `digcancel.recent(since)` stays the damp/warm record; its matcher takes a caller rect, so the
     watcher passes the fort bounds or per-block rects.
4. **Existing consumers to adjust.** The dig-progress and stuck-job census treat designations outside
   the site as noise or "stalled". Classify auto tiles as `auto_followed`, the same fix
   `cancelled_by_game` got.
5. **Prospecting pass (roadmap idea).** Because following starts only from a dug vein tile, and plain
   rock cannot be auto-designated in the UI, a prospecting pass is a standard sparse dig pattern
   (exploratory-mining rows, see wiki "Exploratory mining") with `dig_auto` on all of it. It follows
   only what the pattern's tiles actually touch.
