# Official "Modern" (Steam-style) Graphics on the Free DF Classic Build

Date: 2026-09-09
Scope: Dwarf Fortress Classic 0.53.16 (ITCH build, `www.bay12games.com/dwarves/df_53_16_linux.tar.bz2`, the exact archive `scripts/install_df.py` installs on VM 103), DFHack 53.16-r1.1
Status: research only. No VM was touched; nothing below was tested live. This closes out the open question left by this session's earlier live finding (`decisions/DECISIONS.md` 2026-09-09, the `USE_CLASSIC_ASCII:NO` rows) about whether that finding is a bug to work around or a hard distribution boundary.

## Bottom line

**No official path exists for free.** The modern/Premium tileset is not a separate downloadable asset bundle Bay12 or Kitfox gives away — it is proprietary commissioned art (Carolyn Jong and Neoriceisgood, per the itch.io store listing) that ships only inside the **paid** Premium build (Steam, $29.99, or itch.io, same price, DRM-free). The free Classic distribution — the exact one this project installs — ships with **zero content in `raw/graphics`** by design, not as an oversight or a missing-file bug. `USE_CLASSIC_ASCII:NO` is a real, working renderer switch, but flipping it on Classic asks the engine to draw per-tile sprite graphics from a folder that Classic never populates, which is why the map viewport came back solid black in this session's earlier testing (confirmed independently in the wild: a Steam Community thread reports the identical symptom from a Classic/Bay12 install and gets the identical explanation — see Evidence, Q2).

There is a middle path worth naming precisely because it is *not* the third-party-pack fallback: someone who **legitimately buys** Premium (itch.io's DRM-free Linux build, same version 0.53.16 as this project's Classic pin) could copy that Premium install's `raw/graphics` folder onto the free Classic install run by `install_df.py`, since both are confirmed to be the same codebase with graphics as swappable data, not a code fork. That is official Kitfox art, obtained through an official (if paid) channel — categorically different from an LNP/Meph-style community reskin — but it is not free, and this project's public-repo/no-committed-binaries convention means those asset files could never be checked into this repo even if purchased (see §3).

## Q1 — Does an official separate graphics bundle exist, and how does Steam/Premium actually relate to Classic?

**Answer: there is no separate downloadable bundle. Steam and itch.io "Premium" is the identical codebase to free Classic, with a proprietary tileset+music pack bundled into that one paid distribution, not a different renderer or different game.**

Evidence:
- Kitfox's own itch.io store page for the Premium build (`kitfoxgames.itch.io/dwarf-fortress`) confirms: currently version **53.16** (matching this project's Classic pin exactly), price **"$29.99 USD or more,"** DRM-free, Windows and Linux, and describes the bundled content explicitly as "an all-new tileset featuring brand new pixel art by artists Carolyn Jong and Neoriceisgood" plus a 15-track soundtrack. *Confidence: verified against the primary storefront page.*
- The Kitfox devlog "Classic Mode is here! + The Team Grows" (itch.io devlog) states outright that Classic mode is "a toggle within the same paid build" — i.e. Premium owners can flip to ASCII/Classic-style glyphs inside their paid copy — and separately confirms free Classic remains "on the Bay 12 website, as per usual," implying the free copy and the paid copy are siblings of one codebase, not that Classic gained the paid tileset. *Confidence: verified against the primary devlog, WebFetch-summarized rather than read in full — treat the exact wording as paraphrased, the substance as solid since it's corroborated by the storefront page and the forum evidence below.*
- A Steam Community discussion thread (`app/975370` general discussions) has a commenter stating: "Premium is the same thing as the free version, but with a built-in graphics+music pack (and on Steam specifically, also has integration with the Workshop)." *Confidence: forum folklore, but internally consistent with the two primary sources above and with this session's own live symptom (Q2) — treated as corroborating, not load-bearing on its own.*
- This project's own decision log already independently confirmed the "same codebase" framing from a different angle: `decisions/DECISIONS.md` 2026-08-25 records that `PRINT_MODE:TEXT` has not existed since v50 "in either the Steam or Classic build," i.e. this repo already knew Steam and Classic share engine internals before this research pass.

So to directly answer the two-part question: (a) no, there is no official graphics bundle distributed separately from a game purchase — you cannot download "just the tileset" from Bay12, itch.io, or Steam; (b) Steam's "modern graphics" is **not** purely a renderer/UI default difference — Steam/Premium genuinely ships additional proprietary asset files (the tile-page images and their `raw/graphics/*.txt` definitions) that free Classic's archive does not contain at all. `USE_CLASSIC_ASCII` is the shared renderer toggle both builds expose, but toggling it only does something useful on the build that actually has graphics data to switch to.

## Q2 — Is the empty `raw/graphics` folder really the blocker, or is it a missing setting?

**Answer: the empty folder is the real blocker. This is confirmed both by this session's own prior live testing and independently by an identical, previously-reported community symptom on the exact free/Bay12 distribution.**

Evidence:
- This project's own prior live testing (`decisions/DECISIONS.md` 2026-09-09, the two `USE_CLASSIC_ASCII` rows) is the strongest evidence available, because it was run against the actual install this project uses, not a general claim about the game: `dfhack.screen.readTile`'s buffer for the map viewport came back **4641/4641 tiles blank** with `USE_CLASSIC_ASCII:NO` set, confirmed by a screenshot taken directly off the Xvfb display (bypassing the VNC/relay chain, ruling out a display-layer bug), and reverting only that one setting (leaving a font-file change in place) immediately restored full colored terrain on two different screens. *Confidence: verified, primary source, this project's own DFHack API reads and screenshots.*
- Independently, a Steam Community discussion titled "No Graphics," (`app/975370/discussions/0/3761101693151265727`) describes a user who downloaded DF from the Bay12 website (the free version) and got a black screen in world-gen/menus when trying to use graphics mode, exactly matching this project's symptom. The explanation given: *"The bay 12 version doesn't have graphics, that's the entire purpose of buying the steam version... Both versions have the same content and updates, besides graphics and music,"* and that the only way to get official graphics is to buy the paid build. *Confidence: forum discussion (not an official source) but the reported symptom, on the same free-Classic distribution, is functionally identical to what this project independently measured with DFHack instrumentation — corroborating, not the primary evidence.*
- The DF wiki's "Graphic set" article (`dwarffortresswiki.org/index.php/Graphics_set`) documents the mechanism generically: graphic sets live in `raw/graphics`, each one is a `graphics_<name>.txt` file with `[OBJECT:GRAPHICS]`, `[TILE_PAGE:...]` (image file + tile dimensions + page layout), and `[CREATURE_GRAPHICS:...]` entries that map creatures/tiles to positions on those tile-page images. This is a **data-only** mechanism — it does not describe any separate "graphics mode" engine code path beyond reading these files — which is consistent with the earlier working hypothesis (this session's background) that the map viewport wants real tile-page data, not just a differently-shaped font. *Confidence: verified against the wiki's description of the mechanism, though the WebFetch summary could not confirm whether this exact wiki page currently documents version-53.x specifics or an older version's syntax — treat the tag names as broadly correct DF-graphics-system knowledge, not confirmed byte-for-byte against 0.53.16's actual raw format.*
- No missing init.txt/data setting was found anywhere in the wiki, the itch.io/Steam sources, or the forum threads that would make Classic's map render with `USE_CLASSIC_ASCII:NO` in the absence of `raw/graphics` content. Nothing suggests a font-only or settings-only fix exists. **Not fully verified**: I did not find (and could not fetch) DF's own bundled documentation text describing precisely what happens internally when `USE_CLASSIC_ASCII:NO` is set and `raw/graphics` is empty (i.e., whether this is a documented fallback-to-blank behavior or simply undefined/unhandled) — the wiki's "Settings" page for this version is thin and explicitly says the authoritative descriptions live in `data/init/init_default.txt`'s own comments, which is a local file, not something I fetched from the web. This project's live DFHack read-back is nonetheless direct evidence of the actual behavior, which is the stronger form of confirmation anyway.

Verdict, stated plainly: this is not a bug and not a settings gap. It is `raw/graphics` being genuinely, deliberately absent from the free Classic distribution, exactly as intended by Bay12/Kitfox's Classic/Premium split.

## Q3 — Is there a legitimate way to obtain and install the official raws?

**No free legitimate path. A paid legitimate path exists and is worth describing precisely, because it is meaningfully different from the third-party fallback even though it costs money.**

What buying itch.io's Premium build and copying its `raw/graphics` folder onto this project's Classic install would involve, given what's confirmed above:

- **Source**: `kitfoxgames.itch.io/dwarf-fortress`, "$29.99 USD or more," DRM-free Linux build, currently version 53.16 — the same version number this project's `install_df.py` pins Classic and DFHack to (`DF_VERSION = "0.53.16"`, `DFHACK_VERSION = "53.16-r1.1"`). *Confidence: version-number match verified against the primary storefront listing; whether the Linux Premium binary is byte-identical to the Linux Classic binary beyond version number was not verified — see the DFHack caveat below.*
- **What to copy**: per the Graphics_set mechanism (Q2), the whole `raw/graphics/` directory (tile-page PNGs plus their `graphics_*.txt` definition files) from a Premium install into the Classic install's `raw/graphics/`, then set `USE_CLASSIC_ASCII:NO` in `prefs/init.txt` (the setting this project already knows how to apply via `step_init` in `scripts/install_df.py`). Premium's own default `init.txt`/`d_init.txt` may set other graphics-adjacent keys (tile-page-driven `FONT`/`GRAPHICS_FONT` values, window sizing tuned to the tile pixel size) that would also need copying or matching by hand — **not verified**, since no Premium install was available to inspect in this research pass; treat as "probably needs more than the one folder" rather than "definitely only the one folder."
- **DFHack compatibility concern, specific to this project's exact pin**: DFHack hooks the game via compiled memory offsets against the `dwarfort` executable itself, not via `raw/graphics` (a pure data folder DF's own renderer reads, untouched by DFHack). Copying only asset/data files between two installs of the same DF version should not affect DFHack at all, provided the Classic *executable* installed by `install_df.py` is left alone and only the Premium *data files* are layered on top of it. The real open question is whether Premium's `dwarfort` binary is the same build DFHack 53.16-r1.1 was compiled against — this project's install script already treats that distinction as meaningful (`DF_VERSION_STRING = "v0.53.16 linux64 ITCH"`, with a comment noting "a Steam build would say otherwise, and would not match this DFHack"). That comment is this project's own prior finding, not something re-verified in this pass, but it directly implies mixing Premium's binary in would be a real compatibility risk, whereas mixing in only Premium's `raw/graphics` data alongside the existing, already-verified Classic/DFHack pairing should not be. **This distinction (copy data only, never the executable) was not tested live and should be verified against a live install before being treated as settled.**
- **Repo-policy consequence, not a technical one**: even if purchased, Premium's tileset/music files are proprietary commissioned art with no stated redistribution license found anywhere in this research (the itch.io page's fetched content had no EULA text). This repo is public (`CLAUDE.md`: "This repo is public... Infrastructure specifics... go in gitignored `infra/local.*`"). Proprietary purchased game assets are a sharper version of the same problem the repo already has conventions for — they must never be committed to this repository, purchase receipt or not; if this path is ever taken, the asset files belong entirely outside git (parallel to how `infra/local.*` is already gitignored), and the decision to spend money on them is a call for the user, not something to do unprompted.

## Q4 — Is this a genuine hard limitation of free Classic, and what's the actual mechanism?

**Yes, plainly: this is a hard limitation by design, not a technical accident.** The mechanism, stated once clearly: Dwarf Fortress since the 2022 Steam/Premium launch is one codebase with two distributions. Both read `raw/graphics` through the same generic tile-page/creature-graphics system (Q2) and both expose the same `USE_CLASSIC_ASCII` toggle in `init.txt`. Premium's distribution bundles a commissioned, proprietary tileset (and music) into that folder; free Classic's distribution — confirmed both by this project's own live install and by the itch.io/Steam sources — ships that folder empty. There is no code difference gating "modern graphics" behind Steam specifically (no Steam-only rendering path, no DRM check in the renderer); it is purely a case of one distribution shipping art assets the other does not. Buying either Steam or itch.io Premium is buying exactly those asset files (plus a Workshop integration on Steam specifically, and a soundtrack) layered onto the same game.

This project's `Working.md`/`decisions/DECISIONS.md` conclusion to leave `USE_CLASSIC_ASCII` at whatever `init_default.txt` ships (YES, ASCII-style-but-modern-UI-elsewhere) and use only the bundled square font for a crisper look, is therefore the right call to leave standing — there is no missed official setting or file that would unlock real per-tile terrain sprites for free.

Per the task's scope, the fallback is only noted, not designed: the standard community route (LNP-bundled packs, or Meph's Vanilla Expanded and similar) works because the exact same `raw/graphics` mechanism documented in Q2 is open to anyone — community tilesets are graphic sets built with the identical `[TILE_PAGE]`/`[CREATURE_GRAPHICS]` tags Kitfox's own Premium pack uses, just drawn by different artists and given away free. That remains available as a later, separate piece of work if the user decides free-but-third-party is an acceptable tradeoff; this research does not design it further.
