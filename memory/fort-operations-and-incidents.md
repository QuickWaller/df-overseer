### 2026-09-11: Labor management primitives built: get_unit_status/set_labor

**Status:** accepted, verified live against Uniboslan

**Reason:** Picks up the 2026-09-11 gap row above (`ROADMAP.md` Later bucket) — the first concrete build against it. Checked, not assumed, before writing any logic: `manipulator`/`gui/manipulator` both confirmed `Tags: unavailable` on this exact install (grepped their doc files live over SSH), `autolabor` confirmed genuinely available (`hack/plugins/autolabor.plug.so` present, its own doc carries no `unavailable` tag) — matches what the earlier row asserted, now checked against the primary source rather than repeated on trust. One implementation surprise: `df.unit_labor` is an enum wrapper, not a plain Lua table — `pairs()` over it yields internal fields (`_first_item`, `attrs`, ...) rather than labor entries; the working approach iterates numerically from `_first_item` (`-1`) to `_last_item` (`93`, confirmed live) and reverse-looks-up each name via `df.unit_labor[code]`. This closes the one primitive `research/2026-08-25-spatial-perception.md` §5 flagged as unverified for `get_unit_status` (raw `flags1/2/3` bit-guessing for hostile detection) with something strictly better, not just something confirmed: `dfhack.units.isDanger`/`isInvader` are real, documented, present-on-this-install functions — no raw flag reading was needed at all. Deployed via plain `scp` onto `hack/scripts/` (same pattern as the blueprints row, since `install_df.py` had uncommitted changes in flight from a concurrent peer session at the time — a proper `install_df.py`-driven deploy subcommand, matching `ui-install`'s pattern, is the natural next step, not yet done). `near_landmark` is deliberately omitted from `unit-status`'s output for now — the landmark system lives only on `perception-layer-experiments`, a different session's branch, not merged to `main` — raw `x,y,z` is printed instead. **Read-only and mutation both done entirely over `dfhack-run lua`/RPC, no `xdotool` or simulated mouse/keyboard input at any point** — chosen specifically so this could run safely alongside the user's newly-live personal-control VNC session (row above) without contention on the shared X11 input channel. `autolabor` itself was not enabled — confirming it's available and building the manual primitives underneath it was this session's scope; turning it on is a separate decision.

### 2026-09-11: autolabor enabled on Uniboslan, verified persisted

**Decision:** **Enabled `autolabor` on Uniboslan, user's go-ahead** — verified genuinely on, verified persisted via a real quicksave, and found a new save-rotation behavior in the process

**Status:** accepted, verified live

**Reason:** Read `autolabor`'s own doc before touching the live fort rather than assuming: enabling it disables the vanilla work-detail system and has it recalculate labors on its own cycle, **explicitly leaving dwarves on active military duty or assigned to a burrow untouched** — the actual, primary-sourced answer to "does autolabor fight the manual `set-labor` calls from the row above," found in the tool's own docs rather than needing a live experiment to discover. Confirmed genuinely disabled first (`autolabor status` → "the plugin is not enabled"), enabled (`enable autolabor`), then confirmed genuinely enabled afterward (`autolabor status` → real data, "6 IDLE, 1 OTHER") rather than trusting the "Enabling autolabor" message alone. `pause_state` checked before and after: unchanged (still paused). The doc states the enabled flag survives save/reload, implying it's written into the save itself, not just live in DFHack's process memory — quicksaved to confirm this for real rather than leaving it assumed. **Found a new, previously-undocumented behavior doing so**: `quicksave` rotates forward through the `autosave N` slot pool by one call each time rather than overwriting the currently-active slot in place — two quicksaves in a row moved `df.global.world.cur_savegame.save_dir` from `autosave 1` → `autosave 2` → `autosave 3`, each with a fresh mtime matching when it actually ran (confirmed via `stat`, not assumed from the RPC call returning cleanly — this repo's own documented trap that a quicksave can report success before the file lands). This is distinct from, and less alarming than, the Artobcatten incident (`decisions/DECISIONS.md` 2026-09-10): that was two *different forts* colliding on one shared slot pool; this is one fort rotating forward through its own slots exactly as designed, nothing overwritten unexpectedly, nothing lost — but it does mean any future mtime-based "did my save land" check should re-read `cur_savegame.save_dir` fresh each time rather than assuming a slot name checked earlier is still the current one. Not yet checked: whether `autolabor` actually starts moving idle dwarves onto jobs once the fort is next unpaused and actively driven — only its status output and the persistence question were verified this session.

### 2026-09-11: First real combat: unit-status hostile missed a kea attack entirely

**Decision:** **First real combat on Uniboslan: a kea attacked, the fort's dogs and a fisherdwarf killed it — and `unit-status hostile` missed the entire event, before, during, and after**, confirming the "isDanger is broader/narrower than actual threat" caveat with a second, much stronger real case

**Status:** accepted (documented, no code change yet)

**Reason:** The user spotted the fight live via the viewer and asked for it to be used as a real test case rather than a synthetic one. Reconstructed from `gamelog.txt` (153 lines total, real per-blow combat text): a kea (unit 321) picked a fight near the fort; the stray dog, a stray war dog, and citizen 196 ("Solon Tabarsazir, Fisherdwarf" — matches `profession="Fisherdwarf"`) all engaged it; the war dog eventually "shakes the kea around by the lower body...the lower spine collapses," an artery opens, and the kea dies. Confirmed directly against live unit state, not the log text alone: `dfhack.units.isDead(unit 321)` → `true`; one dog (id 201) shows a real `body.wounds` entry (matches the log's "denting the skin and bruising the muscle") but is alive; the fisherdwarf herself shows zero wounds — she landed a hit (her iron pick literally "lodged firmly in the wound") but took none. **The actual finding**: `unit-status hostile` (this session's own script, row above) was run both before this fight was found and immediately after — in both checks it reported exactly the same 4 deep-cavern `DEMON_*` units as the *only* "hostile" hits, at every point completely blind to a kea that was, in ground truth, actively fighting and killing things at the fort's own front door. Checked directly, not assumed: all 9 live `BIRD_KEA` units on the map, including the one that just died, read `isDanger=false, isInvader=false` — DFHack's own predicates simply do not classify an ordinary aggressive-wildlife skirmish as danger at all, while they *do* classify harmless, un-encountered deep-cavern demons as danger (the inverse of what "hostile" needs to mean for a fort-defense purpose). This is worse than the first case's caveat (isDanger being *too broad*) — here it is **too narrow**, silently missing a real, fort-relevant threat entirely, in both directions on the same day. **Not fixed this session, on purpose** — this is a documentation/finding pass, not a rebuild; the natural fix is almost certainly event-driven (`docs/PURPOSE.md` build order item 5, `get_diff_since` via the `eventful` plugin, not specced yet) rather than a better predicate-based `unit-status hostile` filter, since the actual signal that mattered here was "something attacked something," which is inherently an event, not a queryable static-world-state predicate. `research/2026-08-25-spatial-perception.md` §5's `get_unit_status` spec gets an inline correction note pointing here.

### 2026-09-11: Root cause of quicksave silent no-op: async render-loop-gated overlay

**Decision:** **Root-caused the quicksave "silent no-op": it's an async, render-loop-gated overlay, not a synchronous save call — the two apparent no-ops were most likely just longer lag, not a distinct failure**

**Status:** accepted (root cause), **downgrades the two rows above from "confirmed silent no-op" to "unresolved, likely lag"**

**Reason:** User's own reaction to the earlier finding ("id be suspicious here") was right to take seriously rather than wave off — dispatched a `researcher` subagent (Sonnet) to actually dig in rather than let it sit as an assumption. Read the installed `quicksave.lua` directly (independently re-verified against the live file in this session, not just the subagent's quote): `quicksave` pushes a `QuicksaveOverlay` screen via `gui.Screen`; the actual `save()` call — which sets `plotinfo.main.autosave_request`/`autosave_timer` and prints "The game should autosave now" — only runs inside that overlay's own `:render()` method, on a later game render pass, not synchronously with the RPC call. Live-reproduced under quiet conditions (paused, no VNC activity, nothing else running): a `quicksave` call returned exit 0 with **no** log trace at all for over 45 seconds, then the save landed for real (slot rotated, fresh mtime) — directly falsifying this project's own working assumption that "no log line + no mtime change within a few dozen seconds" means "no-op." A second live reproduction completed within 8 seconds — the delay is genuinely variable, not a fixed constant; the leading (not fully source-confirmed) explanation is contention on DFHack's single main scripting thread, which also runs 10 frequently-firing stock `control-panel/fix/*` repeat scripts confirmed live via `repeat --list`. Honestly flagged, not glossed over: the two *historical* no-ops' true fate is now unrecoverable (only 3 save slots exist, overwritten oldest-first, already overwritten by later real saves), so "they also landed late" can't be proven over "they truly did nothing" — the claim is downgraded to unresolved-likely-lag, not silently upgraded to fully-explained. Full evidence trail, ranked hypotheses, and exact UTC timeline: `research/2026-09-11-quicksave-silent-noop.md`. **New verification protocol, replacing the old "wait a few seconds"/"retry" advice**: poll the active save slot's `world.sav` mtime for up to ~90 seconds, and never treat `stderr.log`'s "Invoking:"/"should autosave" lines as reliable either way — proven unreliable in both directions this session.

### 2026-09-11: pause_state flip explained: the user's own VNC session, not a mystery

**Decision:** **Resolved a live concern the quicksave investigation surfaced on its own: an unexplained `pause_state` flip during the investigation was the user's own legitimate use of the new control channel, not a mystery agent — and asking about it surfaced and fixed a real, separate logging bug**

**Status:** accepted, verified

**Reason:** The quicksave subagent (row above) found `df.global.pause_state` flip `true→false` mid-investigation with no VNC activity logged in that window and no action of its own — flagged as a real concern rather than assumed benign, per this session's own standard of treating "id be suspicious here" seriously. Asked `df-automation-e6` directly rather than guessing. Answer, corroborated independently in this conversation (the user had already mentioned watching a live kea fight around the same general period, consistent with actively driving the game): the user really was connected via the personal-control VNC channel and unpaused the fort themselves — exactly what that channel is for, not unannounced concurrent access. **A genuinely useful side effect of asking**: e6 found and fixed a real bug the investigation's own "no VNC activity logged" observation had been silently relying on being accurate — both x11vnc instances (`df-vnc` since 2026-09-09, `df-vnc-control` since 2026-09-11) were writing to the identical log file (`X11VNC_UNIT`'s log path wasn't parameterized per-service), so the log genuinely went silent once the second process attached to it, independent of whether real input was happening. Confirmed by e6 via `ps`/`systemctl show` showing both processes' identical `-o` log path, and the file's own mtime matching the investigation's "nothing since 00:48:04" finding. Fixed (each instance now gets its own log file), redeployed, and the public feed reconfirmed untouched (`HTTP 200` throughout) — committed and pushed as `65a96fc`. Net effect: the pause-flip is explained and benign; the "no VNC activity" evidence that made it look unexplained was itself broken, now fixed, so future investigations of this kind won't hit the same false negative.
