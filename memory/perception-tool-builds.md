### 2026-09-10: Citizen-centroid Embark Site seed landmark (experimental)

**Decision:** **Proposed, explicitly experimental: a citizen-centroid "Embark Site" seed landmark, bootstrapping the landmark system on a fort with no burrows or buildings yet**

**Status:** **proposed, experimental** — user's own framing: "willing to try it" but "view this as experimental," not a settled design

**Reason:** User raised a real gap in `docs/PURPOSE.md` build order item 3 (the landmark system on burrows): every downstream tool that expresses results relative to a named landmark (`find_open_area`'s `near` param, `get_connectivity_report`'s `near_landmark` field) has nothing to anchor to on a virgin embark, since burrows/buildings only exist once something has actually been dug or built — the build order's own sequencing implicitly assumed at least one landmark already exists by the time it matters, without saying how the first one is created. User also asked whether a full 3D world representation would be readable by the model; answered from evidence already in this repo rather than guessing: `evals/perception/` (the eval harness) already compared three representations (named-landmark exit lists, a coordinate table, and prose) and deliberately did not build a full-grid/ASCII-map arm, because the cross-domain research behind it (`research/2026-08-25-spatial-perception.md` §2, citing BALROG, the NetHack Learning Environment, Voyager, robotics scene-graph work) already converged on transformers not reliably reconstructing spatial adjacency from a flattened grid regardless of encoding (pixels or JSON) — a dense per-tile 3D dump would be the map-rendering problem in a different serialization, not an escape from design commitment #1. Checked the proposed fix for a real embark before writing it: `df.global.world.vehicles.all` is confirmed **empty** for this exact embark (Uniboslan) — no wagon object exists to anchor to, ruling out a wagon-position-based seed as unreliable. Citizen positions are reliable instead: live read showed 7 citizens in a tight cluster (`x` 94-100, `y` 91-99, `z` 169 uniformly), so the seed landmark is their centroid, computed once and persisted via `dfhack.persistent.saveSiteData` (the same site-scoped mechanism `warn-stranded.lua` already uses for its own state) under `scripts/dfhack/df-overseer-landmarks.lua` (`list`/`get NAME`, deployed via the now-generalized `install_df.py ui-install`). **Verified live, not assumed**: first call computed `(96, 96, 169)` (matches a hand-computed centroid of the 7 read positions); a second call returned the identical value without recomputing (confirms persistence is read, not recalculated live each time, which matters since citizens move); then quicksaved, fully stopped and restarted the systemd service (not just re-querying the same running process), reloaded via "Continue active game," and confirmed the exact same `(96, 96, 169)` came back — genuine save-file persistence, not an in-memory cache. **A real bug was found and fixed in the process**: querying `list` immediately after triggering the reload (before the map had actually finished loading) hit the error path in `list_landmarks()`, which returns two values `(landmarks, err)` on failure; the CLI's original `print(json.encode(list_landmarks()))` implicitly passed both return values into `json.encode(data, options, msg)`, so the error *string* landed in the `options` parameter and crashed inside `pairs(options)` (`table expected, got string`) — fixed by destructuring the two return values explicitly at the call site rather than splatting them positionally into a function with different per-argument meanings. This is explicitly the first slice only (one seed node), not the full burrow/building enumeration + adjacency-graph system build order item 3 actually calls for — real burrows and buildings become additional landmarks once anything exists to name, this just gives `find_open_area` and friends something to anchor the very first dig to.

### 2026-09-11: find_open_area (terrain=built) built (item 6)

**Decision:** **`find_open_area` (terrain="built") built — `docs/PURPOSE.md` build order item 6**

**Status:** accepted, verified live

**Reason:** New `scripts/dfhack/df-overseer-openarea.lua`: a `near`-landmark-anchored, radius-capped (hard cap 60, clamped in code not just documented) scan for WxH windows of free tiles (walkable via `dfhack.maps.getWalkableGroup`, confirmed live `0` on a solid wall vs a real group id on open floor; no building via `dfhack.buildings.findAtTile`, confirmed live `nil` on open floor vs a real pointer on the existing stockpile).
