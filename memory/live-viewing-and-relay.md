# Live viewing and relay

The live-view/relay/VNC/streaming build: screenshot capture, the relay VM, the tunnel plus noVNC chain, the Steam-graphics transplant, and the personal-control VNC channel. Long register rows moved here 2026-09-15.

### 2026-09-08: Live-view screenshot capture built and verified

**Decision:** **Live-view screenshot capture built and verified on VM 103**, `install_df.py stream` — periodic `import`, real PNG confirmed by pulling and viewing one

**Status:** accepted, verified

**Reason:** Follows `research/2026-09-08-live-viewing.md`'s recommendation: a systemd oneshot service + timer (not a long-lived process) captures `import -display :99 -window root` to `/opt/df/stream/latest.png` on an interval (default 15s), with `dfhack-run` enabling `spectate` first so the camera is pointed at something happening. Two real bugs found and fixed in the same pass, both now baked into `scripts/install_df.py`: (1) the temp file was named `latest.png.tmp` — ImageMagick's `import` infers output format from the file extension, `.tmp` isn't recognized, so it silently wrote a 6 MB PostScript file instead of a PNG with no error; fixed with an explicit `png:` format prefix rather than relying on the extension. (2) `/opt/df/stream/` was created under `sudo` (root-owned) but the capture service runs as `User=df`, so the first real run failed with `Permission denied`; fixed by chowning the directory to the guest user in the same setup script. Verified for real: pulled `latest.png` to the workstation and viewed it — the DF title screen, 1280x800, matching the live VM exactly. **Ingest (push to willsmith.nz) is not wired up yet** — `willsmith.nz` is a static GitHub Pages site with no backend (per the research), so `DF_STREAM_INGEST_URL` needs to point at something that can actually receive an upload. User is provisioning a Cloudflare R2 bucket for this; once live, the push side (`curl -F` in the capture script) will need converting to an S3-compatible signed upload rather than a plain multipart POST, since R2 doesn't accept the latter. A standalone static viewer page was added to `willsmith-portfolio` at `public/dwarf-fortress/index.html` (committed locally there, not pushed/deployed) — polls for `latest.png` with a cache-busting query string, reports "not wired up yet" honestly rather than a broken image until the R2 URL is filled in.

### 2026-09-09: Relay VM built on Debian, not Alpine

**Decision:** **Relay VM built on Debian 12 (bookworm genericcloud), not Alpine** — `scripts/provision_relay.py`, vmid 105 (`df-colony-relay-01`), `<relay-vm-ip>`, home-lab pool, `srv-01`

**Status:** accepted, verified

**Reason:** User chose Alpine first (smaller than Ubuntu; LXC was ruled out separately for this specific box, since it's slated to eventually be the estate's one internet-facing thing and LXC's shared-kernel isolation is a weaker boundary than a VM's). Built successfully, but SSH auth failed for every candidate user (`relay`/`alpine`/`root`) with a clean `Permission denied (publickey,keyboard-interactive)` despite a fully healthy sshd and correct network config from the same NoCloud datasource (confirmed by SSH reaching exactly the assigned static IP, not a DHCP coincidence). A cheap Sonnet research pass (not guesswork) found the root cause against Alpine's own `README.Alpine` for its `cloud-init` package: Alpine's cloud-init locks the account password by default, and Alpine's `openssh` package is built without PAM, which makes OpenSSH refuse pubkey logins on a locked account regardless of a correctly-installed key — a narrow, specific bug in the user/ssh-key stage, not a general cloud-init failure (the network-config stage from the same datasource ran fine). Both real fixes (`openssh-server-pam` + `UsePAM yes`, or explicit `lock_passwd: false`) require a custom cloud-init snippet; Proxmox's REST API has no endpoint to upload snippet content (confirmed via the Proxmox support forums — a known, requested-but-missing feature), and the standard workaround is placing the file directly on the Proxmox host's filesystem via SSH, which is exactly the access no agent has here (home-lab's "no agent SSH to either host, for anything" rule). Rather than ask a human to do that one-time manual step, pivoted to Debian 12 bookworm's `genericcloud` image: same apt/dpkg ecosystem as the rest of this project (websockify 0.10.0+dfsg1-4 and novnc 1:1.3.0-1 confirmed available via packages.debian.org before switching), still meaningfully lighter than a full Ubuntu server image, and Debian/Ubuntu's PAM-enabled `openssh-server` has no equivalent lock-vs-pubkey interaction (cross-checked: no matching bug report found for Debian or Ubuntu cloud images). Verified end to end: SSH as the `relay` user works cleanly. Image pinned to a dated build (`20260907-2594`, not `latest`), checksum fetched and grepped directly via `curl` rather than through an LLM-summarized fetch — a checksum is exactly the kind of value that must not pass through a paraphrasing step, learned from nothing going wrong here but worth stating as the standard now. `scripts/provision_relay.py` reuses `provision_vm.py`'s generic helpers (`read_pubkey`, `wait_for_status`, `resize_disk`, `destroy_failed_build`) under its own `RELAY_*` `.env` prefix, kept fully separate from VM 103's `DF_*` vars so rebuilding one can never collide with the other.

### 2026-09-09: LAN live-viewing chain completed: tunnel plus relay VNC

**Decision:** **LAN live-viewing chain completed: reverse SSH tunnel (VM 103 → relay) + relay-side websockify/noVNC, verified end to end** — `install_df.py vnc-tunnel`, `provision_relay.py webvnc`

**Status:** accepted, verified

**Reason:** Implements `research/2026-09-09-reverse-vnc-relay.md` §5's recommended design over the VNC-repeater chain. `vnc-tunnel` generates a dedicated ed25519 keypair on VM 103 itself (private key never leaves it, distinct from the admin key used to manage either box), installs only the public half on the relay's `authorized_keys` restricted with `permitopen="127.0.0.1:5900",no-pty,no-agent-forwarding,no-X11-forwarding` (per the research's stated design — even a fully compromised copy of this key can only ever forward to that one loopback port, nothing else), and runs `ssh -N -R 127.0.0.1:5900:127.0.0.1:5900` as `df-vnc-tunnel.service`, `Requires=df-vnc.service`. Verified independently from the relay's own loopback (not VM 103): connecting to `127.0.0.1:5900` there returned a real RFB handshake, proving the tunnel genuinely bridges to VM 103's `x11vnc` rather than just reporting an active systemd unit. Confirmed live before deploying: the relay's sshd already has `AllowTcpForwarding yes` and `GatewayPorts no` (checked via `sshd -T`, not assumed) — the latter is exactly why the tunnel's remote listener binds to the relay's loopback only, not its LAN interface, giving two independent layers (kernel-level bind scope, plus the key's own `permitopen` restriction) rather than relying on either alone. **Caught and fixed before it shipped**: `install_df.py`'s existing `NOVNC_UNIT` template hardcoded `After=df-vnc.service`/`Requires=df-vnc.service`, correct on VM 103 (where x11vnc is a local sibling unit) but naming a unit that doesn't exist at all on the relay (where the port is reached only through a tunnel from a different host) — `Requires=` on a genuinely absent unit fails the requiring service to start, not merely warns, which would have broken the relay's own `df-webvnc.service` silently. Fixed by parameterizing the dependency block (`%(depends)s`) rather than forking a second copy of the template, so VM 103's and the relay's calls each supply the dependency line that's actually true for that host. `provision_relay.py webvnc` installs `websockify`/`novnc` (same Debian package versions already confirmed) and reuses `NOVNC_UNIT` with `After=network.target` only. Full chain verified live: `df-vnc.service` active, `df-vnc-tunnel.service` active, `df-webvnc.service` active, `http://<relay-vm-ip>:6080/vnc.html` returns HTTP 200. Not yet verified: the actual in-browser WebSocket→RFB round trip (no browser available in this session).

### 2026-09-09: Custom bitmap font superseded (broke map rendering)

**Decision:** **Superseded same session, see the row below**: `FONT`/`FULLFONT:curses_square_16x16.png` + `USE_CLASSIC_ASCII:NO`** in `scripts/install_df.py`'s `INIT_SETTINGS` — reverted, then the actual bug (isolated to `USE_CLASSIC_ASCII:NO` alone) was found and fixed

**Status:** **superseded** (same day, by the row below)

**Reason:** Tried for a nicer look through the newly-working VNC viewer; looked low-risk (a bitmap font already bundled in the pinned, checksummed DF install, no new download, no `raw/graphics` folder exists on this build at all so no sprite-graphics-pack compatibility question even applied). Broke world-map rendering completely instead of just looking different — confirmed three independent ways: DFHack's own `dfhack.screen.readTile` buffer for the map viewport read back entirely blank (4641/4641 tiles `ch=0` or space — checked as aggregate counts only, not printed terrain content, to stay inside design commitment #1 even for this diagnostic); a screenshot taken directly off VM 103's Xvfb display via `import` (bypassing the VNC/relay chain entirely) showed the identical solid black, ruling out a VNC-side bug the user rightly suspected first; reverting just those three keys and restarting DF immediately restored full colored terrain on both the world overview and the Site Finder screen, confirmed by direct before/after screenshots. Left `INIT_SETTINGS` without those three keys (whatever `init_default.txt` ships is what's used) rather than hunting for a working alternative bitmap font in the same session — a real graphics/tileset upgrade deserves its own research pass, not a quick swap assumed harmless because the file happened to already be present. **Also the occasion for an explicit, scoped exception to design commitment #1's absolute wording**: the user directly asked to compare screenshots for this debugging purpose and stated that reasoning from a rendered map is fine for the humans/agent designing the system, distinct from the agent's own perception during actual unattended play — this doesn't change the commitment itself (still queued for its own proper `decisions/DECISIONS.md` entry per the 2026-09-09 handover), but is the first concrete instance of the distinction being exercised on purpose rather than left as an abstract open question.

### 2026-09-09: Official Steam-graphics transplant onto Classic install

**Decision:** **Official Steam-graphics transplant onto VM 103's free Classic install — confirmed working, real per-tile sprite art rendering** — `install_df.py graphics` (new subcommand) plus `GRAPHICS_MODULES`/`INIT_SETTINGS` in `scripts/install_df.py`

**Status:** accepted, verified

**Reason:** `research/2026-09-09-df-modern-graphics.md` (same day) had already closed off any *free* official path: Premium's tileset is proprietary Kitfox-commissioned art bundled only in the paid Steam/itch.io build, and free Classic ships `data/vanilla/vanilla_*_graphics`/`vanilla_world_map` as empty `info.txt`-only stubs by design, not a bug — confirmed independently by this project's own prior live `USE_CLASSIC_ASCII:NO` testing (solid-black map) and by a matching community report. What changed the calculus: the orchestrating session found the user already owns a legitimate Steam copy locally (`C:\Program Files (x86)\Steam\steamapps\common\Dwarf Fortress`, confirmed version **53.15**, one patch behind VM 103's pinned 53.16) — personal-use asset data from a purchase already made, not a new spend. **Legitimacy basis**: the user's own purchased copy, copied for personal use onto infrastructure the same user controls, never redistributed, and never committed to this (public) repo — `cmd_graphics` tars the eight module folders locally, `scp`s the tarball straight to the guest, and deletes the local temp file; the asset bytes never touch this repo's git tree or working directory at any point. **Mod-selection mechanism**: none was needed. The originally-anticipated hard problem (DF v50+'s mod-selection screen requiring UI automation to opt a graphics module into a world's mod list) turned out not to apply here — VM 103's own `gen_modlist.txt` from its existing (pre-transplant) world already listed all eight `vanilla_*` modules as active with no mod-selection UI ever touched, confirming these vanilla modules are baked into every worldgen unconditionally, not opt-in like a Workshop mod. The task was therefore pure file-placement (populate the stub folders DF already reads) plus `USE_CLASSIC_ASCII:NO` (already-known-safe from the prior finding once real data backs it), not screen automation — DFHack's mod-manager/`enable-mod` question this task set out to research became moot. **Version gap**: 53.15 source data layered onto a 53.16 Classic executable/DFHack pairing; verified safe by design (DFHack hooks the executable's compiled memory offsets, untouched here — only pure data/PNG/raw-text asset files were copied, never the `dwarfort` binary itself) and empirically, by results: DFHack stayed fully functional throughout (viewscreen introspection, `find_param` struct writes, mouse-click automation all worked normally post-transplant) and the rendering itself is visibly correct, not corrupted or misaligned. **Verification, not just a viewscreen-type check**: real screenshots (saved locally, `C:\Users\wills\df-graphics-screenshots\`) on three separate screens — the world overview, the unzoomed Site Finder panel, and the zoomed embark-placement map — all show genuine pixel-art sprites (trees, water with wave texture, mountains, a volcano, sand) rendering in full color, not blank/black tiles and not ASCII. One honest caveat recorded rather than glossed over: `dfhack.screen.readTile`'s aggregate non-blank-tile count, the exact diagnostic this project used to *prove the bug* in the original `USE_CLASSIC_ASCII:NO` investigation (0/4641 non-blank), reads back **0 again** over the equivalent clean map-only region in this now-confirmed-working case — meaning that specific screen's terrain is drawn via a texture/sprite-blit path invisible to `dfhack.screen`'s character-buffer instrumentation, and the readTile check is not a valid signal for this particular widget either way; the screenshot is the load-bearing evidence here, not the buffer read. Also recorded honestly: this exact task was started by an earlier agent this session that was interrupted mid-way with no final report — its actual stopping point was reconstructed rather than assumed, by direct live inspection of VM 103 (process list, current viewscreen, `data/vanilla/` module file counts, `prefs/init.txt`) before any further action, per this repo's own "verify the verification" rule; that inspection found the interrupted agent had already completed the graphics transplant, the `USE_CLASSIC_ASCII:NO` flip, and a full fresh worldgen (`region2`, discarding the old ASCII-era candidate site per the user's prior approval) all correctly, leaving DF idle at the title screen with nothing stuck or mid-write. This session's work was completing the remaining, unverified half: the visual confirmation and a fresh Site Finder pass on `region2` (§ below). Two follow-up questions the user raised live via the VNC feed while this work was in progress were investigated directly rather than assumed: (1) whether DF's v50+ button-style menus expose per-screen keyboard hotkeys (checked via screenshots and `pen.fg` colour dumps on the Site Finder panel, world-map buttons, and the title menu — no bracketed/underlined/distinctly-coloured hotkey letter found anywhere, confirmed programmatically via uniform `fg` values, not just a visual glance); and (2) whether a global keyboard-vs-mouse interface-mode toggle exists (checked Settings' Video/Game/Keybindings tabs in full, including scrolling the Game tab to its actual end — `Keybindings` is confirmed to be a physical-key **rebinding** screen for named actions already known dead against these widgets, not an interaction-mode switch; no such toggle exists anywhere in Settings or in `prefs/init.txt`/`data/init/d_init_default.txt`, and the one `KEYBOARD_CURSOR` flag that does exist governs only the in-fortress designation cursor per prior research, not menu navigation). Both came back negative, confirmed by direct live testing rather than by inference — the existing buffer-scan-and-click mouse automation (`decisions/DECISIONS.md`'s 2026-09-09 title-screen-bootstrap row) remains the correct and only mechanism for these screens, and for the Site Finder's search criteria specifically, a direct struct-field write (`scr.find_param[2] = 0`, the `gui/embark-anywhere.lua`-style idiom) proved more robust than hunting for a `+`/`-` button's screen coordinates (which, unlike the Video settings tab's, do not appear to render as static text/icon glyphs on this particular panel at all). **Result**: `find_results` flipped from `-1` to `2` ("Match found!") on `region2` with `Savagery` set to `Calm`, a real candidate site highlighted on the map — not yet embarked, per the task's explicit instruction not to.

### 2026-09-11: Personal-control VNC channel deployed and verified

**Decision:** **Personal-control VNC channel actually deployed against VM 103/the relay, and the user's own Cloudflare dashboard step completed — real authenticated mouse/keyboard control of the live game confirmed working**

**Status:** accepted, verified independently, not just relayed

**Reason:** Completes the row above. Deployed by a peer session (`df-automation-e6`, commit `05aaf01`) using a second, independent Cloudflare Tunnel (`cloudflared-admin.service` on the relay — `cloudflared`'s own `service install` wrapper targets one fixed unit name, so a second `cloudflared tunnel run --token` unit was built instead of overwriting the public tunnel) rather than modifying the existing `cloudflared.service`. The user completed the one step this repo cannot do for itself: Zero Trust → Access → Applications → a self-hosted app for `dwarf-fortress-admin.willsmith.nz`, an Allow policy scoped to their own email, "Browser rendering (RDP/SSH/VNC)" deliberately left off (that Cloudflare feature tunnels a raw protocol port directly; this channel already goes through noVNC's own web client over HTTP, so it doesn't apply and would have been the wrong config) — confirmed by the user getting a real Access email-code prompt before reaching anything, not silently passed through by their own already-logged-in Cloudflare account. **Verified independently in this session, not taken on the peer's word alone** (this repo's own "verify before relaying" rule): `systemctl is-active` on VM 103 confirmed `df-vnc-control.service` and `df-vnc-control-tunnel.service` both `active`; an unauthenticated `curl` of `https://dwarf-fortress-admin.willsmith.nz/` returned `302` (redirected to the Access gate, not served plain) while the existing public `https://dwarf-fortress.willsmith.nz/` still returned `200` unaffected — the actual observable a broken or bypassed gate would fail to produce, not just a "looks fine" glance. Full chain: `dwarf-fortress-admin.willsmith.nz` → Cloudflare Access (email OTP) → `cloudflared-admin` on the relay → `df-webvnc-control.service` (`127.0.0.1:6081` only) → reverse SSH tunnel → VM 103's `df-vnc-control.service` (port 5901, real input, no x11vnc password — Access is the only gate, deliberately, one sign-in not two). **Two live layers now exist on top of the one fort**: the pre-existing public view-only feed (unauthenticated, `-viewonly`, unaffected) and this new authenticated full-control feed for the user alone — both confirmed live simultaneously. **Standing caution restated because it is now live, not hypothetical**: any future `xdotool`/DFHack-fake-input use against VM 103 shares this exact control channel and can visibly fight a connected human session; this session's own labor-management work (see the row below) deliberately stayed on `dfhack-run lua`/RPC only for this reason, never touching mouse/keyboard input, specifically so it could run concurrently with the user driving the game live through this new channel.
