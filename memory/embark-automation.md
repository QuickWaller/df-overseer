### 2026-09-09: Title-screen bootstrap without a pixel-coordinate exception

**Decision:** **Title-screen bootstrap: no exception to design commitment #1 needed — a code-only label locator replaces the pixel-coordinate approach**

**Status:** accepted, verified

**Reason:** The title screen's main menu turned out to be mouse-click-only (three keys tested live against `viewscreen_titlest`, zero effect — `SELECT`, `MENU_CONFIRM`, `STANDARDSCROLL_DOWN`; process confirmed actively rendering via `/proc/<pid>/stat` CPU-time delta, ruling out a stalled game loop). The naive fix (a hardcoded pixel coordinate read off a screenshot) would have been a real exception to commitment #1 ("never show the model a rendered map... hard commitment, not a preference"); the user was asked directly and chose to pause rather than decide in the moment. A four-agent (Opus-orchestrated, Sonnet-executed) cross-domain research pass followed — `research/2026-09-09-title-screen-bootstrap-exception.md` — surveying RPA/browser-test conventions, general bootstrap-vs-steady-state exception patterns (PKI key ceremonies, MISRA deviations, Kubernetes init containers, Rust `unsafe`), LLM computer-use literature, and roguelike-bot precedent (NLE, BotHack, Angband's Borg, df-ai). Consistent thread across all four: don't grant the exception, look harder for a way not to need one — reinforced by MISRA's own answer to this exact shape of problem (an init-time invariant violation) being "redesign it away," not "grant a deviation." That way existed: `dfhack.screen.readTile` returns real tile data across the whole title screen (confirmed live, 1326/1326 non-nil), meaning `gui/kitchen-info.lua`'s shipped label-locator technique applies directly — scan the character buffer for a button's literal text, derive the click coordinate from that scan, never from an image. Live-verified end to end: scanning for letter-range characters found "Start new game in existing world" at row 33, columns 63-94 (center x=78); setting `df.global.gps.mouse_x/mouse_y = 78, 33` plus `gui.simulateInput(scr, '_MOUSE_L')` flipped `scr.mode` from `MAIN_MENU` to `CONTINUE_INACTIVE`, landing on the world/region list, itself also read via the same buffer-scan technique (`World: Thadar Thran, "The Planets of Dawning" / Folder: region1`). No image was produced or consulted at any point in the working path — this is not a permitted exception to commitment #1, it's a demonstration the exception was never necessary. One tested-and-rejected side path, worth not repeating: hovering the virtual mouse over a button does **not** update `scr.selected` (tested at two different button rows, no change) — there is no click-free hover-calibration loop on this screen; the buffer-scan-for-text-then-click approach is the one that works. → `Working.md`'s "Live-tested 2026-09-09" section for full detail.

### 2026-09-10: Two embark coordinate frames found; xdotool needed for real mouse input

**Decision:** **Root cause of the whole night's map-navigation confusion found: `find_mm_*` (Site Finder's match output) and `neighbor_hover_mm_*`/`warn_mm_*` (the real, committable embark rectangle) are two different coordinate frames, not interchangeable** — confirmed live, not inferred, and DF's headless map/hover rendering is proven to depend on real X11 mouse input DFHack's own fake input cannot provide, with `xdotool` found and validated as the fix

**Status:** accepted, verified, one sub-question left open

**Reason:** Full detail in `research/2026-09-10-embark-screen-rendering-and-coordinates.md`. Chain of discovery, live with the user watching over the public feed: (1) confirmed `df.global.gps.precise_mouse_x/y` (the real, pixel-level mouse state that DF's map rendering, hover-info panel, and WASD panning all depend on) never updates via DFHack's `gui.simulateInput` — it's polled from the real OS mouse every frame (`enabler.get_precise_mouse_coords`), and there is no real mouse in headless Xvfb, so it sits permanently frozen; (2) installed `xdotool` and confirmed real X11 input injection against the Xvfb display (`DISPLAY=:99 xdotool mousemove/keydown/keyup`) genuinely updates it, unblocking real map hover, real terrain-info readouts, and real WASD camera panning, none of which DFHack's fake input could ever drive — calibrated the DF window's exact `+0,+40` offset within the virtual display via `xwininfo`, confirmed exact via `xdotool getmouselocation` cross-checked against `precise_mouse_x/y`; (3) found `xdotool`'s own `click` action has no inter-step delay in this version (confirmed via its own docs), explaining why bare `mousemove+click` was flaky while an explicit `mousemove` → `sleep` → `mousedown` → `sleep` → `mouseup` sequence was reliable; (4) despite all of this working, an embark placed via forced `warn_mm_* = find_mm_*` still landed on bad terrain (a throwaway ocean/aquifer diagnostic site, confirmed unusable, the user flagged it live before any commitment) — this was because `warn_mm_*` and `neighbor_hover_mm_*` are confirmed (via a live match against `location.embark_pos_min/max`, whose real decompiled names are literally `abs_mm_start`/`abs_mm_end`) to be **world-absolute** embark-tile coordinates, while `find_mm_*` is a **smaller-magnitude, non-absolute** coordinate that was never safe to write into `warn_mm_*` directly — the exact mechanism was never a camera/rendering problem, it was silently treating two differently-scaled fields as interchangeable. A subagent's live X-axis check (`location.region_pos.x * 16 + find_mm_sx`) matched exactly, consistent with the DF Wiki's "one region tile = a 16×16 grid of embark tiles," but the Y-axis was off by a consistent, unexplained 9 from a non-time-aligned sample (`doing_site_finder` was already `false` when read) — left explicitly unresolved rather than forced into a clean story; the research file's single recommended next step is one atomic read of `find_mm_*`/`neighbor_hover_mm_*`/`region_pos` taken immediately after a fresh "Begin," which would settle it. Also found live: the `doing_site_finder` flag is the best-supported (though not conclusively proven) gate for the green "acceptable sites" overlay's visibility, independent of `find_results` staying valid; and two previously-undocumented fields, `setting_up_map_timer`/`animating_quick_start_timer`, are a plausible (unconfirmed) gate on why toggling `zoomed_in` via a raw struct write usually doesn't visibly re-render the local view while a real click sometimes does. **Practical resolution, not blocked on the open Y-axis question**: since a real `xdotool` click already produces a correct, world-absolute `warn_mm_*` directly, the plan going forward is a text-only "sweep" — move the real cursor to successive candidate tiles, read the already-proven-reliable hover-info panel and placement-warning text (both plain character-buffer text, zero image dependency, consistent with design commitment #1), and commit the first candidate that both matches desired criteria and comes back clean — rather than ever reconstructing `find_mm_*`'s exact transform.

### 2026-09-10: Text-only embark sweep; a Windows SSH transport bug

**Decision:** **Built the text-only embark-site sweep, found a Windows-specific SSH transport bug while deploying it, and found a genuinely strong second-site candidate** — nothing committed, both left for the user's own go/no-go call

**Status:** accepted (tooling + bug fix), verified; **candidate site proposed, not committed**

**Reason:** Extended `df-overseer-ui.lua` with three subcommands (`embark-mode`, `leave-embark-mode`, `hover`) implementing the sweep plan from the prior row. First deploy attempt (`install_df.py ui-install`) failed **silently** — exit 0, "deployed" logged, but the file on the guest was untouched (stale mtime) and the remote command's own stdout was the literal, un-decoded base64 payload. Root cause, confirmed by reproducing it in a 40-line isolated script: `remote()`'s `echo <base64> | base64 -d | bash -s` pattern embeds the whole payload in the SSH command-line argument, and Git's MSYS-linked `ssh.exe` silently truncates that argument to ~8182 characters when spawned by a **native Win32 process** (Python's `subprocess`, which must flatten argv into one `CreateProcess` string) — but not when spawned by a **POSIX process** (bash, which execs the real argv array directly); a raw bash-invoked `ssh` with the identical, longer payload did not truncate. This was a latent bug the whole time, just never hit before because every prior `remote()` payload (including the first, smaller `ui-install`) happened to stay under ~8KB. **Fixed** in `provision_vm.ssh_guest` (new `input_data` param, piped to the child's stdin) and `install_df.remote()` (payload now goes over stdin, never embedded in the command string) — `provision_relay.py` inherits the fix for free since it reuses the same `remote()`. Verified: re-ran `ui-install`, file landed correctly (211 lines, correct mtime), all three new subcommands worked live. Live-drove the sweep itself: confirmed a **new, previously undocumented mechanic** — `neighbor_hover_mm_*` only live-updates from real mouse movement while `scr.choosing_embark` is `true`; during ordinary zoomed browsing it is frozen even though the hover-info text panel itself still updates live in both modes (the prior research pass's live confirmation of this field came from an actual embark-placement click, inside `choosing_embark` mode, not from casual hovering — this generalizes it). Also confirmed **`LEAVESCREEN` cleanly cancels `choosing_embark` mode** with no side effect (`warn_mm_*` still `-1,-1,-1,-1` afterward) as long as the map itself is never clicked, and that **WASD camera panning works fine while `choosing_embark` is `true`** — no need to leave the mode to pan between sweep samples. Navigated the camera from its idle position (deep in open ocean, `zoom_cent≈251,216`) back toward the original Site Finder match area (`region_pos 9,5`, absolute `~150,79`) and ran a 5×5-point raster there: found real land immediately, no ocean anywhere in that viewport (`Temperate Shrubland`/`Temperate Conifer Forest`/`Mountain`, several points with `aquifer=0`). Best candidate, full-detail-checked: **absolute embark rectangle `sx=128 sy=84 ex=131 ey=87`** (`neighbor_hover_mm_*`, the confirmed world-absolute frame) — Temperate Conifer Forest, Warm, Heavily Forested, Thick other vegetation, **DF's own "Recommended size" flag present**, Deep soil (Clay/Sand), no aquifer, full mineral suite (Iron/Gold/Silver/Copper/Nickel/Zinc/Platinum/Tin/Lead) plus a Flux stone layer (steel-capable); the one real caution is hostile Goblins "a short trip east." Left the screen clean and idle afterward (`leave-embark-mode` confirmed, `warn_mm_startx` still `-1`, `choosing_embark` false) — **nothing committed**. Per this repo's rule that hard-to-reverse actions need explicit confirmation, and `Working.md`'s own open three-way question (keep both forts, abandon the first, or move on), actually embarking this candidate is left for the user, not auto-executed.

### 2026-09-11: Corrected: mode's unavailability doesn't block re-embark automation

**Decision:** **Corrected an overstated claim: "`mode` is unavailable, so unattended re-embark is blocked" is wrong — `mode` is nearly irrelevant to re-embark, and the real gaps are narrower and closer to buildable than `docs/PURPOSE.md` used to say**

**Status:** accepted, **researched, corrected**
