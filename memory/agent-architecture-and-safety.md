# Agent architecture and safety

Agent-architecture findings: the pause-vs-throttle game-time argument, why a specialist role's value is context partitioning, and the two safety detectors built but not yet run. Long register rows moved here 2026-09-15.

### 2026-09-12: Pause-vs-throttle unit: game time per decision, not wall-clock latency

**Decision:** **The unit for choosing between pause and throttle is game time elapsed per decision, not wall-clock tool latency. Throttling does buy thinking time after all**

**Status:** accepted, **user's correction to this session's own conclusion**

**Reason:** Minutes after the row above concluded that throttling "trades game speed for agent latency rather than buying thinking time outright", the user pointed out the obvious thing it had missed: throttling delays tool calls, but it also gives the agent more time to think per unit of *game* time, which is the only currency the fortress experiences. Working it out: for a cycle that thinks for `T` seconds and makes `k` tool calls at frame cap `f`, thinking costs `f·T` ticks (the game runs while the model thinks) and each tool call costs about one tick regardless of `f` (it waits for the next suspend window), so **game time per cycle is roughly `f·T + k` ticks**. Three consequences. (1) Lowering `f` shrinks the `f·T` term **linearly**, down to a floor of `k` ticks, so throttling genuinely does buy thinking time, and the wall-clock price is paid by the human watching rather than by the fort. (2) Pause remains the only lever that reaches zero game time. (3) **Choose on the shape of the cycle rather than on urgency**: a think-heavy cycle (long deliberation, few calls) benefits from throttling almost linearly, while a call-heavy cycle cannot get below the `k`-tick floor and gets much worse in wall-clock (`k/f`), so pause it instead. **A fourth consequence is a real optimisation nobody had noticed**: `CoreWakeup.wait()` waits until `toolCount` reaches zero, so every suspender pending at the same instant is serviced in one window, meaning `k` sequential calls cost about `k` ticks while `k` concurrent calls cost about one. Batching independent reads is therefore game-time-efficient as well as token-efficient, which is an argument for the single-snapshot read pass that has nothing to do with snapshot consistency. Scale caveat recorded so this is not over-tuned: at `FPS_CAP:5` a tick is 200ms while measured round trips were 0.66-1.28s, so transport overhead currently dominates and the arithmetic only bites at low `f` or high `k`.

### 2026-09-12: A specialist role's value is context partitioning, not judgment

**Decision:** **A specialist role's value is context partitioning, not differentiated judgment. The "accepted without modification" trigger proposed for folding a role in is withdrawn as measuring the wrong thing**

**Status:** accepted, user's correction

**Reason:** This session predicted that the first real run would show the Overseer doing everything useful while the Architect proposed things it already knew, and offered a trigger: fold the role in if its proposals are accepted unmodified more than ~80% of the time. The user corrected the premise: an advisor can hold more detail, more tools and its own doctrine **without cluttering the decider's context**, which is a different value proposition that the acceptance rate does not test at all. A specialist accepted 100% of the time can still be earning its place if what it does is keep a large doctrine set out of the decider's prompt. **The session had already made this argument itself earlier the same day** ("the roster is itself a compression scheme") and then contradicted it, which is recorded here rather than quietly dropped. Two things strengthen the user's version beyond the general point. First, **doctrine, not tool output, is the dominant context cost**: tool output is transient while doctrine loads every cycle, and room-siting doctrine alone is substantial, so a monolithic decider holding siting plus military plus stock plus arbitration rules walks into the cliff `evals/compliance/` measured at n≥40 rules. Second, and found by re-reading the allowlists this session had just written: **the Overseer holds `openarea.build`/`diggable.dig` but NOT `openarea.find`/`diggable.find`/`chokepoints.find`, so it can act on a candidate and cannot discover one.** The division is enforced by the permission layer rather than being a convention, which makes the Architect structurally necessary and the original prediction wrong mechanically, before judgment is even considered. **Replacement tests, in increasing order of trust:** (1) does the decider's context stay roughly flat as roles are added, since a growing prompt means the partition is leaking; (2) is each role's doctrine large enough to be worth a round trip, since a five-rule role is pure overhead and there is a floor below which it should be folded in; (3) **A/B one recorded snapshot through a monolithic Overseer versus the three-role roster, comparing total tokens and decision quality.** Note that (3) is only affordable because advisors are read-only and snapshots are replayable, so a property argued for on consistency grounds turns out to be what makes the roster's own value falsifiable.

### 2026-09-12: Safety detectors built (threat, breach); neither has ever run

**Decision:** **Both safety detectors built and landed: `df-overseer-threat.lua` and `df-overseer-breach.lua`. Neither has ever been run**

**Status:** accepted as code, **unverified, not deployed**

**Reason:** Closes the "required build work" the capability brief created, in code only. **Threat detector**: admission is by **reachability, never by a danger flag**, per this session's design call. A unit qualifies if it shares a `getWalkableGroup` id with a living citizen OR sits within a bounded distance of a named landmark, the two OR'd because each covers the other's blind spot (group-sharing models ground pathing only, so a flyer reads group 0; landmark distance is geometric and does not imply reachability on a tall fort). `isDanger`/`isInvader`/`isAgitated`/`isGreatDanger` are read, reported, and labelled `HEURISTIC` **in the tool's own output**, extending §10's reliability vocabulary from manifest metadata into runtime data, and used only as a ranking tiebreak. Deliberate accepted consequence: a harmless songbird inside the walkable network will appear, ranked low; real wildlife noise volume on a populated fort is unknown. Exclusions are `isDead` plus `isOwnCiv` or `isFortControlled`, the latter new to this repo and corroborated against three shipped scripts on the exact installed build. **Breach detector**: two-stage because the Sentry polls it every few seconds. Stage 1 reads one bool per map block across the map's **fixed** block count, so its cost does not grow with dig progress, which is the load-bearing efficiency claim. Stage 2 scans only flagged blocks. Severity comes from a **rise** against a session-scoped `_G` baseline, so a well's static water alarms once on seed and never again, escalating on adjacency to the citizen walkable network and on magma. Reviewed here rather than accepted on report: coordinate discipline confirmed correct (raw coordinates computed and consumed internally, output carries only `near_landmark`/`direction`/`distance_tiles`, and the internal `_G` baseline key never surfaces), and both files carry the `--@module = true` guard `docs/TRAPS.md` requires.
